# ADR-0022. Выкладка статики

Статус: принято 16 октября 2026 по рекомендации.

Вопрос: как файлы иконок попадают на CDN так, чтобы пользователи никогда не получили половину обновления?

Решение:

- Конвейер собирает папку выпуска по схеме из ADR-0004: файлы иконок, SVG и `checksums.json` с отпечатками всех файлов версии.
- Выгружаются только новые файлы: старые версии неизменяемы, перезаписывать их нельзя.
- Порядок: сначала все файлы версии, затем сверка контрольных сумм и только в конце — `manifest.json`. Пока манифест не обновлён, пользователи видят прежнюю версию целиком.
- Откат — возврат манифеста к предыдущей версии. Файлы старых версий хранятся 12 месяцев (ADR-0005).
- Выкладка запускается из CI после слияния PR с данными, а не с чьего-то компьютера.

Уточнение от 21 октября 2026 (шаг 1 фазы 2, `pnpm cdn build`):

- Папка выпуска — `dist-cdn/` в корне репозитория, в git не хранится. Раскладка по ADR-0004: `manifest.json`; `v/{версия}/{набор}/{имя}.json` и `.svg` на каждую иконку и каждый алиас, скрытые тоже — имена не пропадают (ADR-0005); `v/{версия}/{набор}.checksums.json`.
- Файл сумм лежит рядом с папкой набора, а не внутри: внутри он притворялся бы иконкой, а имена `info`, `icons`, `search` у наборов реально есть; точка в имени иконки невозможна, конфликт исключён. Содержимое — `{"algorithm":"sha256","files":{"{набор}/{имя}.json":"<64 hex>",…},"prefix":…,"version":…}`, пути относительно `v/{версия}/`.
- `{имя}.json` — IconifyJSON для одного имени: `prefix`, `width`, `height` (и `left`/`top`, если есть у набора), `icons` с иконкой, у алиаса ещё `aliases` со всей цепочкой; записи — как в `icons.json`; компактно, ключи отсортированы. Без `lastModified`: версия его не учитывает (ADR-0018), а папка версии должна быть чистой функцией версии, иначе одна и та же версия могла бы дать разные байты. Дата последнего выпуска — только в манифесте, её и читает ядро (ADR-0030).
- `{имя}.svg` — как у SVG-адреса Iconify без параметров: `<svg xmlns="http://www.w3.org/2000/svg" width="1em" height="1em" viewBox="0 0 24 24">…</svg>`, высота `1em`, ширина — пропорция, округлённая вверх до сотых (`0.97em` при 32×33), как в ADR-0031. Повороты и отражения в данных не поддерживаются: при их появлении набор получает «СТОП», а не тихо неверный SVG.
- `manifest.json` — `{"sets": {набор: {"version", "lastModified"}}}`, читаемо, наборы по алфавиту.
- Без изменений — без записи: набор пропускается, если его файл сумм на диске тот же и в папке столько же файлов; иначе файлы пишутся во временную папку рядом, подменяют старую целиком, а файл сумм пишется последним — он и есть признак целой папки. Манифест перезаписывается только при отличии. Повторная сборка не меняет ни байта.
- Порядок локальной сборки: наборы → манифест → уборка `v/` (версии не из манифеста, забытые временные папки). Манифест до уборки, чтобы он никогда не указывал на удалённое; правило «манифест последним» выше — про выгрузку, оно остаётся.
- Хоть один набор остановлен — манифест не пишется и уборки нет; старые файлы набора не трогаются.
- Проверено 21 октября 2026: пять наборов — 88 654 файла (36 127 иконок и 8 200 алиасов), 68 МБ, первая сборка около 30 с на Windows, повтор без изменений — 2 с.

Уточнение от 22 октября 2026 (шаг 2 фазы 2, `pnpm cdn upload`):

- Выгрузка — команда `pnpm cdn upload [--dry-run]`: сначала сборка `dist-cdn/` как в `pnpm cdn build` («СТОП» сборки — выгрузка не начинается), затем бакет R2 `iconavo-cdn`, к которому подключён домен `cdn.iconavo.dev`. Ключи — `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`: локально в `.env`, в CI — секреты GitHub Actions; токен «Object Read & Write» только на этот бакет. Запросы подписываются своим кодом по AWS Signature V4 (`packages/pipeline/src/cdn/sigv4.ts`, проверен на официальных примерах Amazon), без зависимостей: ключ хранилища — самый чувствительный секрет проекта, через чужой код он не проходит (решение владельца 22 октября 2026).
- Файлы версии читаются с диска по файлу сумм, и каждый сверяется с SHA-256: лишний или битый файл — «СТОП» набора с подсказкой «запустите pnpm cdn build».
- Сравнение с бакетом — по списку объектов (ListObjectsV2): файл «на месте», если совпали размер и ETag с MD5 содержимого (у обычной загрузки ETag — MD5, как в S3); нет в бакете — выгружается; есть, но другой — конфликт и «СТОП» набора: в `v/` ничего не перезаписывается никогда. Смена формата файлов уже выложенной версии даст такой конфликт — тогда нужна новая схема адресов, решать при первом случае.
- Запись: `Content-MD5` в каждом запросе, так что повреждённую загрузку отвергает сам сервер; `Content-Type` (`application/json; charset=utf-8`, `image/svg+xml; charset=utf-8`) и `Cache-Control` по ADR-0023 хранятся у объекта и отдаются с домена. 32 записи одновременно; 408, 425, 429, 5xx, сбой сети и таймаут 60 с — до 5 попыток с паузой 1, 2, 4, 8 с или по `Retry-After`; 401 и 403 — «СТОП» всего прогона с подсказкой про ключи. Ключи не печатаются, из сообщений об ошибках вычищены.
- Порядок в наборе: файлы → файл сумм последним (в бакете он появляется, только когда все файлы версии на месте) → сверка по списку ещё раз. Манифест — в самом конце, только если ни один набор не остановлен и он отличается от того, что в бакете. Ничего не удаляется: старые версии остаются (ADR-0005), уборка — отдельный шаг позже.
- `--dry-run` — сравнение с бакетом без записи; ключи нужны и для показа: список бакета без подписи не отдаётся.
- Запуск из CI — workflow «Выкладка» (`.github/workflows/deploy.yml`): `push` в `main`, когда менялись `data/**`, код раздачи или сам workflow, и вручную с флажком «только показ». Выгрузки не пересекаются и не прерываются: следующая ждёт текущую. На PR не запускается — секретов там нет. Страницы `upload.html` и `build.html` — артефакты запуска.
- Первая полная выгрузка — разовое исключение из правила «только из CI»: с компьютера владельца по ключам из `.env`, чтобы проверить запись на настоящем R2 до слияния PR (решение владельца 22 октября 2026). Дальше — только CI.
- Откат — откат PR с данными: `pnpm cdn build` соберёт манифест с прежней версией, выгрузка допишет только его, файлы прежней версии в бакете на месте.
- Отчёт — `.cache/reports/cdn/upload.html` и таблица в терминале. Константы — `packages/pipeline/src/cdn/config.ts`, код — `src/cdn/sigv4.ts`, `s3.ts`, `upload.ts`, `upload-report.ts`.
- Проверено 22 октября 2026: первая выгрузка с компьютера владельца — 88 659 файлов, 68 МБ, 44 мин 28 с (около 33 файлов в секунду при 32 параллельных записях; из CI ожидается быстрее). Сверка после записи сошлась у всех пяти наборов: ETag у R2 равен MD5 содержимого, как в S3. Повторный показ — «без изменений» у всех наборов и манифеста, 1 мин 34 с на чтение списков. С домена `cdn.iconavo.dev` файлы отдаются с заданными `Content-Type` и `Cache-Control`; JSON Cloudflare пока не кэширует (`cf-cache-status: DYNAMIC`), заголовков CORS нет — шаг 3.

Уточнение от 22 октября 2026 (шаг 4 фазы 2, второй хост, ADR-0025):

- Выгрузка идёт на два хоста: бакет R2 (`cdn.iconavo.dev`), затем хранилище Bunny (`cdn2.iconavo.dev`).
- «Все файлы версии, затем сверка» — теперь на обоих хостах. Только после этого пишутся манифесты: сначала R2, второй хост — последним. «СТОП» на одном хосте — манифесты не пишутся нигде.
- Сверка на Bunny — SHA-256 из списка хранилища против файла сумм; на R2 — по-прежнему ETag = MD5.
- Ожидание задачи «Выкладка» — 90 минут, с запасом на первую полную выгрузку на новый хост.
- Ручной запуск с другой ветки выгружает, только если `data/` там та же, что в `main`; «только показ» — с любой ветки.
- Откат по-прежнему — откат PR с данными: манифесты обоих хостов вернутся к прежней версии.

Уточнение от 30 октября 2026 (шаг 2 фазы 4, каталог наборов для edge API, ADR-0024):

- **Зачем.** Адресам `/collections`, `/collection` и `/changelog` нужны сведения о наборе, категории, скрытые имена, алиасы и выпуски. В файлах иконок их нет.
- **Где.** Вне `v/`: `info.json` и `metadata.json` меняются и без новой версии набора (версия — отпечаток только `icons.json`, ADR-0018), а папки версий неизменяемы.
  - `catalog/{набор}/{хэш}.json` — готовое тело ответа `/collection` в формате Iconify;
  - `catalog/changelog/{хэш}.json` — последние 100 выпусков всех наборов; `changelog` — служебное слово, набора с таким префиксом не бывает (ADR-0037);
  - `catalog/{хэш}.json` — оглавление: на набор — IconifyInfo, полный текст лицензии и отпечаток тела; ещё отпечаток файла выпусков.

  Имя файла — 12 знаков SHA-256 содержимого, поэтому и файл каталога не перезаписывается никогда.
- **Манифест** получил поле `catalog` — отпечаток оглавления. Манифест пишется последним, поэтому новый каталог включается одним шагом с новыми версиями наборов. Ядро и функция edge API читают только `sets` (проверено по коду). Схема манифеста конвейера принимает и манифест без `catalog` — выложенный до шага 2.
- **Сборка** `pnpm cdn build`:
  - каталог пишется после наборов и до манифеста; без изменений — без записи;
  - из `dist-cdn/catalog/` убирается то, на что оглавление больше не ссылается;
  - нет `metadata.json` или `changelog.json`, или свежий выпуск журнала — не версия `icons.json`, — «СТОП» набора.
- **Выгрузка** — только в R2: каталог читает только edge API, а для `cdn2` понадобились бы новые правила зоны Bunny.
  - Порядок: файлы версий → каталог (оглавление последним, сверка по списку) → манифесты.
  - Другой файл под тем же именем — «СТОП», как в `v/`.
  - Манифест на `cdn2` тот же, с полем `catalog`: ядру это не мешает.
- **Проверка.** `pnpm cdn check` на `cdn.iconavo.dev`: в манифесте есть `catalog`, оглавление отдаётся с кэшем на год, его отпечаток совпадает с именем, наборы — те же, что в манифесте. `pnpm cdn verify` сверяет и каталог в R2.
- **Размер** на 30 октября 2026 — 7 файлов, 1,2 МБ. Самый большой — тело Material Symbols: 712 КБ, в br — 75 КБ.

Почему: обновление для пользователей выглядит мгновенным и цельным, а любую ошибку можно откатить за минуту.

Последствия: шаги 1–2 фазы 2 строятся по этой схеме; после обновления манифеста edge API сам переходит на новую версию — она входит в ключ его кэша, сбрасывать ничего не нужно (ADR-0023, ADR-0024).
