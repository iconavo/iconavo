# ADR-0029. Пакеты: ядро и адаптеры

Статус: технические части приняты 16 октября 2026 по рекомендации, с опорой на Iconify; продуктовая — имена тега и пакетов — подтверждена владельцем 17 октября 2026 (отметка в [сводке решений](README.md)).

Вопрос: из каких пакетов состоит библиотека для разработчиков?

| Пакет | Что делает |
| --- | --- |
| `@iconavo-ui/core` | Ядро без привязки к фреймворку: хранилище, загрузка, рендер SVG |
| `@iconavo-ui/icon` | Веб-компонент `<iconavo-icon>` для любого фреймворка и обычного HTML |
| `@iconavo-ui/react` | Компонент React, который рисует SVG напрямую через ядро |

- Ядро общее для всех адаптеров — так устроен и Iconify, где все компоненты работают на одном ядре ([источник](https://github.com/iconify/iconify)).
- Адаптер React не оборачивает веб-компонент, а рисует SVG сам: так проще серверный рендер, и так же устроен React-компонент Iconify.
- Адаптеры Vue и Svelte делаются после запуска по той же схеме.
- Во время работы у пакетов нет внешних зависимостей.

Продуктовое решение — владельца, подтверждено 17 октября 2026: имена. Рекомендация — по образцу тега `iconify-icon` у Iconify: тег `<iconavo-icon>` и пакеты `@iconavo-ui/core`, `@iconavo-ui/icon`, `@iconavo-ui/react`. Scope в npm — `@iconavo-ui`, потому что `@iconavo` занято; имя тега от npm не зависит. Дефис в имени тега обязателен: этого требует стандарт веб-компонентов.

Уточнение от 26 октября 2026 (шаг 1 фазы 3, README пакета; решение владельца — обёртка `IconavoProvider`):

- **Что ставит разработчик.** Один пакет: `@iconavo-ui/icon` для HTML и любых фреймворков или `@iconavo-ui/react` для React. Оба реэкспортируют из ядра функции `configure`, `addIcons`, `setLoader`, `loadIcons` (ADR-0030) и типы `IconavoIconSet`, `IconavoIcon`, `IconavoAlias` — те же, что у пакетов данных (ADR-0026). Ядро ставится зависимостью, отдельно — только для своих адаптеров.
- **React** — компонент `Icon` (как в ADR-0042 и у Iconify) и обёртка `IconavoProvider` для серверного рендера (ADR-0033).
- **Одна версия и общее хранилище.** Три пакета выходят одной версией. Если на странице оказались две копии ядра — два бандла, два адреса или разные версии 0.x, — в браузере у них одно хранилище иконок и настроек под ключом `Symbol.for` с версией формата. Иначе тег регистрирует первая копия (ADR-0032), а `configure` и `addIcons` второй ни на что не влияют. На сервере у каждого модуля своё состояние. Требование к шагу 2.
- **Публичное API ядра** — только то, что описано в README. Вспомогательные функции, которые `packages/core` сейчас экспортирует для edge API (`calculateSize`, `formatNumber`, `SVG_NS` и другие), в шаге 2 переезжают в `@iconavo-ui/core/internal`: после публикации они стали бы обещанием разработчикам.
- **README** — `packages/icon/README.md`, на английском (ADR-0036).

Уточнение от 27 октября 2026 (шаг 2 фазы 3):

- **Два входа ядра.**
  - `@iconavo-ui/core` — только `configure`, `addIcons`, `setLoader`, `loadIcons` и типы `IconavoIconSet`, `IconavoIcon`, `IconavoAlias`; это проверяет тест.
  - `@iconavo-ui/core/internal` — для наших адаптеров и edge API: проверка имён, разбор `rotate`, `flip` и размеров, `iconData`, `iconToSvg`, `svgToString`, `calculateSize`, `formatNumber`, `SVG_NS` и доступ к хранилищу (`getIcon`, `subscribeIcon`, `loadIcon`, ADR-0030).
- **`"sideEffects": false`** — функция edge API берёт из ядра только сборку SVG, хранилище и загрузка в её бандл не попадают; это проверяет тест сборки.
- **Общее хранилище** — под `Symbol.for("iconavo.core.1")`: иконки, слушатели, настройки и загрузчики. Подробности — в ADR-0030.

Уточнение от 27 октября 2026 (шаг 4 фазы 3):

- **Рендер — в ядре**, во внутреннем входе: `renderIcon` (атрибуты `<svg>` и рисунок строками, без DOM), `setStrokeWidth` и `replaceIds`. Их возьмут тег (шаг 5) и React (шаг 7); правила — в ADR-0031.
- В функцию edge API рендер не попадает, как хранилище и загрузка; это проверяет тест сборки.

Уточнение от 27 октября 2026 (шаг 5 фазы 3):

- **`@iconavo-ui/icon`** — три входа:
  - `index.js` — по умолчанию;
  - `development.js` — по условию экспорта `development`;
  - `script.js` — исходник `dist/iconavo-icon.js` для страниц без сборщика.

  Каждый отдаёт ровно четыре функции README и типы ядра (это проверяет тест) и регистрирует тег (ADR-0032).
- **`@iconavo-ui/core/internal`** для адаптеров отдаёт ещё `store` (настройки `placeholder` и `dev`) и `warn` — предупреждение одно на текст и при двух копиях ядра. Размер ядра от этого не вырос: оба уже были в его бандле.

Уточнение от 28 октября 2026 (шаг 7 фазы 3):

- **`@iconavo-ui/react`** — один вход `.` без `"use client"`: функции и типы ядра, `Icon` и `IconavoProvider` (это проверяет тест). Так `loadIcons` вызывается и в серверном компоненте.
  - Пометка `"use client"` стоит первой строкой у модулей компонентов (`icon.js`, `provider.js`); tsc её сохраняет, это проверяет тест на `dist/`.
  - `"sideEffects": false`: в модулях нет кода при загрузке, лист стилей ставится из эффекта (ADR-0033).
  - peer — `react ^18.0.0 || ^19.0.0`, необязательный peer — `@types/react`.
- **Тег и React делят хранилище**, но не обёртку: иконки `IconavoProvider` видят только компоненты внутри неё (ADR-0033).

Уточнение от 29 октября 2026 (шаг 11 фазы 3): одну версию трёх пакетов ставит `pnpm release bump`, а подготовка выпуска не пропустит разные версии; в архивах тега и React ядро — точной версией выпуска. Порядок выпуска — в ADR-0051.

Почему: логика живёт в одном месте, а каждый адаптер остаётся тонким и простым.
