# ADR-0050. Сайт документации и живые примеры

Статус: принято 29 октября 2026 (шаг 10 фазы 3). Продуктовые решения — владельца: сайт документации — начало основного сайта, до запуска он скрыт от поисковиков, пример Next.js — локально. Технические части приняты по рекомендации.

Вопрос: где живёт документация пакета, пока нет основного сайта, и как разработчик за пять минут видит пакет в деле?

## Сайт

- **`apps/site`** — Next.js 16.4 (App Router), React 19.3, TypeScript 7, адрес `iconavo.dev`. Это начало основного сайта (ADR-0007, ADR-0037): пока на нём только главная и раздел `/docs`, остальное придёт в фазе 4. Решение владельца 29 октября 2026.
- **Документация собирается из README.** Источников два — `packages/icon/README.md` и `apps/api/README.md` (ADR-0036). Карта страниц — `apps/site/lib/docs.ts`:

  | Адрес | Страница | Разделы README |
  | --- | --- | --- |
  | `/docs` | Quick start | вступление, Install, Examples, Live examples |
  | `/docs/reference` | Reference | Attributes and props, Functions, Loading and errors |
  | `/docs/recipes` | Recipes | Recipes |
  | `/docs/iconify` | Coming from Iconify | Coming from Iconify |
  | `/docs/security` | Hosts, privacy and browsers | Hosts, privacy and security; Browsers and frameworks; License |
  | `/docs/api` | Edge API | весь README edge API |

  Если раздел совпадает с названием страницы, он становится её заголовком, а его подразделы поднимаются на уровень выше. Каждый раздел «##» README попадает ровно на одну страницу. Раздел без страницы — «СТОП» сборки с подсказкой, куда его дописать.
- **Разбор Markdown — свой и строгий** (`apps/site/lib/markdown.ts`). Он понимает только то, что есть в README:
  - заголовки `#`–`####`;
  - абзацы;
  - код в ``` с языком из списка;
  - списки «-» с вложением по два пробела;
  - таблицы GFM;
  - цитату в один абзац;
  - внутри строки — `код`, **жирный**, ссылки и «\».

  Незнакомая разметка — ошибка сборки с номером строки, поэтому сайт и GitHub не расходятся молча. Результат — элементы React, сырой HTML не вставляется.
- **Якоря** строятся как у GitHub (`slug.ts`) и сверены с HTML GitHub 29 октября 2026. Ссылки README переписываются на страницы сайта. Неизвестный якорь, относительный адрес или адрес не по https — «СТОП».
- **Страницы статические**: README читается при сборке. Путь к файлу трассировка Next.js не отслеживает, иначе в выкладку попал бы весь репозиторий.
- **Оформление — прототип на токенах** (ADR-0038).
  - Tailwind CSS 4; токены — CSS-переменные в `app/globals.css`, их имена — договор с переменными Figma.
  - Светлая и тёмная темы — по настройке системы.
  - Тест `lib/tokens.test.ts` не пускает в страницы цвета, свои значения Tailwind и атрибуты `style`.
  - Подсветки кода нет: цвета — часть визуального дизайна (фаза 6). shadcn/ui и Storybook — в фазе 4.
- **Иконки сайта — нашим пакетом.**
  - `loadIcons` в layout передаёт их в `IconavoProvider`, и они попадают в HTML страниц.
  - Если хоть одна не загрузилась, сборка падает: иначе вышла бы страница с вечными заглушками.
  - У иконок `className="inline-block"`, как советует README для Tailwind.
- **Доступность — WCAG 2.2 AA:**
  - ориентиры страницы, ссылка «Skip to content», один h1, видимый фокус;
  - широкие таблицы и код прокручиваются внутри области, которая получает фокус;
  - меню на телефоне — `<details>`, работает без JavaScript.
- **Заголовки** (`lib/headers.ts`):
  - CSP в продакшене — как у `examples/next`: стили только файлами, `connect-src` — хосты иконок;
  - `X-Robots-Tag: noindex, nofollow` и `<meta name="robots">` — от одной константы `INDEXING`;
  - `nosniff`, `Referrer-Policy`, `X-Frame-Options: DENY`, `Permissions-Policy` и метка сборки `X-Iconavo-Build`.
- **Скрыт от поисковиков до запуска 1 июня 2027** — решение владельца 29 октября 2026, вслед за «бета без анонса» (ADR-0036).
  - `robots.txt` обход не запрещает: иначе поисковик не прочитал бы и саму метку noindex.
  - В фазе 7 нужно вместе: `INDEXING = true`, ожидания noindex в `pnpm site --check` и `--live`, карта сайта.
- Тариф Vercel **Hobby** — только для некоммерческого использования. До запуска он подходит, а при коммерции нужен Pro за $20 в месяц (фаза 7).

## Живые примеры

- **`examples/starters/{html,react,next}`** лежат вне рабочего пространства pnpm (`!examples/starters/**`). Каждый пример ставит пакеты из npm, как у разработчика: StackBlitz открывает только подпапку и не понимает `workspace:*`. Тексты примеров — английские, меток для проверок в них нет.
- **HTML** — один `index.html` со строками подключения из README. Ссылка — с `?startScript=dev`: в папке есть `package.json` со статическим сервером `servor` 4.0.2 (без своих зависимостей, `--reload` обновляет превью после правки), и StackBlitz запускает его в WebContainer. Сначала ссылка была с недокументированным `?template=html` — статика без установки. Но после выпуска 0.1.0 оказалось, что этот шаблон выполняет внешний `<script type="module">` как обычный скрипт: тег падает на `export`, иконок нет. Тот же файл через `import()` в том же превью работает. 30 октября 2026 владелец выбрал запасной вариант, который был записан здесь заранее: `servor`, новая зависимость только примера. Проверено на StackBlitz: тег зарегистрирован, иконки нарисованы, ошибок нет. Проверка примеров (`pnpm starters --check`) по-прежнему открывает HTML-пример статикой, без установки.
- **React** — Vite 7.3.7, React 19.3.1, TypeScript 7.0.2. Vite 8 на StackBlitz сломан с 25 октября 2026 (wasm-сборка Rolldown), а Vite 7 работает — на него перешёл и собственный стартер StackBlitz.
- **Next.js** — 16.4.3. Проект из примера создаётся у себя командой `npx create-next-app@latest --example https://github.com/iconavo/iconavo/tree/main/examples/starters/next my-icons`. Живой ссылки нет (решение владельца 29 октября 2026):
  - Next.js 16 в WebContainers StackBlitz не запускается ни с Turbopack, ни с webpack (webcontainer-core#1978);
  - а у 15.4.11, которая запускается, по `npm audit` — 30 известных уязвимостей, из них 3 критические.
- **Версии** во всех примерах точные. `@iconavo-ui/*` — версия из адреса скрипта в README (0.1.0).
- **lock-файлы** появятся после публикации (шаг 11): `pnpm starters --lock`. С шага 11 они необязательны: `pnpm release bump` удаляет lock-файлы с прошлой версией, а новые пишутся после публикации (ADR-0051).
- **Ссылки** — из `packages/pipeline/src/starters/links.ts`, вида `stackblitz.com/github/iconavo/iconavo/tree/main/examples/starters/{пример}?…`. Тест согласованности сверяет их с README пакета и README примеров.

## Проверки

- **`pnpm starters --check`**:
  - **Архивы.** `pnpm pack` собирает ядро, тег и React. Чтобы в архив попала сборка, у пакетов появилось поле `"files": ["dist"]`. Состав архива проверяется по самому архиву.
  - **Установка.** npm ставит архивы в копию примера (`.cache/starters`), сборка — скриптами примера. Режимы — разработка и продакшен, браузеры — Chrome, Firefox и WebKit по очереди.
  - **Хосты иконок — превью API этой ветки.** Запросы браузера перехватывает Playwright. Запросы сервера Next.js — подмена `fetch` через `NODE_OPTIONS=--import` (`starters/preload.ts`), в самих примерах её нет.
  - **Что проверяется:**
    - иконки нарисованы;
    - место до загрузки скрипта (HTML);
    - серверный HTML и «без мигания» (Next.js);
    - консоль без ошибок и предупреждений;
    - сеть — только хосты иконок и скрипт тега;
    - подпись «Delete»;
    - axe.
  - **Контрольные запуски:** хосты не отвечают — пустые иконки обязаны быть замечены; испорченный заголовок до гидратации — ошибка обязана быть замечена; у HTML-примера скрипт тега с лишней строкой — браузер обязан его не запустить из-за хэша `integrity` (шаг 11, ADR-0051).
  - **Хэш скрипта в HTML-примере** (шаг 11): в рабочей копии он заменяется хэшем сборки ветки — её проверка подставляет вместо jsDelivr. Хэш из README проверяет режим `--npm` с настоящим jsDelivr.
  - **Находки первого прогона, 29 октября 2026:**
    - строка `:not(:defined)` не знает `width` и `height`, как и написано в README, — поэтому место до загрузки проверка мерит от абзаца текста, а не от страницы;
    - подпись тега через ElementInternals axe не видит — кнопку, где есть только иконка с подписью, axe пропускает, а её имя проверяет дерево доступности Chrome.
  - **`--npm` — после публикации:** пример как есть, `npm ci` из lock-файла, живые хосты, jsDelivr, `npm audit signatures`.
- **`pnpm site --check`**:
  - продакшен-сборка с превью хостов и обход всех страниц по HTTP;
  - по HTTP проверяются коды, заголовки, метка robots, разделы README, ссылки и якоря, статичность;
  - в каждом браузере — иконки в серверном HTML, иконки в строке под стилями Tailwind, консоль и CSP, заголовки страниц, «Skip to content», axe в светлой и тёмной теме, ширина 375 px и кнопка Copy;
  - контрольный запуск подкладывает семь поломок: кнопку без подписи, атрибут `style`, слишком широкий блок, иконку-блок в строке, убранную метку robots, битую ссылку, испорченный заголовок (с шага 1 фазы 4 — одиннадцать, уточнение ниже).
- **`pnpm site --live`** — живой `iconavo.dev`:
  - метка сборки, страницы, заголовки с хостами по умолчанию, noindex;
  - иконки в HTML, разделы и ссылки;
  - сервер Vercel, `robots.txt`, переход с `www` и с `http://`.
- **CI** — задачи `starters` и `site` в `ci.yml`, по браузеру на задачу, параллельно задаче `browser`. Итог `browsers` ждёт все три задачи — это обязательная проверка `main`.
- **Тонкости браузеров:**
  - WebKit, как Safari, по Tab ходит только по полям форм, а ссылки проходит по Option+Tab — у Playwright такого нет. Поэтому там проверяется, что «Skip to content» — первый элемент в порядке фокуса.
  - Нарушение CSP Firefox сообщает и в постороннюю вставку скрипта, поэтому поломки контрольного запуска подкладываются по одной.
  - Кэш Turbopack от сборки с другим окружением ронял `next build` внутренней ошибкой. Поэтому `pnpm site --check` собирает с чистого листа, а кэша `.next` в CI нет.
- **Итог 29 октября 2026** на компьютере владельца — все строки «да» в Chrome, Firefox и WebKit, и у примеров, и у сайта. Кнопку Copy проверяет только Chrome: доступ к буферу.

## Выкладка

- **Через Vercel CLI из GitHub Actions** — workflow «Сайт» (`.github/workflows/site.yml`), а не через Git-интеграцию Vercel. Почему:
  - на машине CI уже стоит pnpm 12, а Vercel его не обещает;
  - выкладка идёт только из `main` через окружение GitHub `site`, как у edge API (ADR-0024);
  - ключ видит только задача, которая не ставит наши зависимости и не собирает код.
- **«Сборка» — без ключа.** `vercel build --prod --standalone` берёт настройки проекта из `.vercel/project.json`, который пишет сам workflow. Проверено 29 октября 2026 на компьютере владельца: Vercel CLI 65.7.0, без ключа, рабочее пространство pnpm 12. Готовая сборка уходит в артефакт архивом tar: он сохраняет символические ссылки функций Next.js.
  - `--standalone` кладёт зависимости функций внутрь сборки (около 6 МБ).
  - Без него сборка ссылается на файлы `node_modules` репозитория (`filePathMap`), а «Выкладка» идёт без репозитория. Так и случилось на первой выкладке 29 октября 2026: проект создался, а выкладка остановилась на «Please ensure project dependencies have been installed».
  - Теперь «Сборка» сама проверяет, что ссылок наружу нет.
- **«Выкладка»** — окружение `site`, свежий Vercel CLI из реестра, `vercel deploy --prebuilt --prod --project iconavo-site --create-if-missing`. Проект создаёт первая выкладка. `apps/site/vercel.json` выключает выкладку Vercel из Git.
- **«Проверка»** — `pnpm site --live --expect-build`.
- **Включение.** Выкладку включает переменная репозитория `SITE_DEPLOY` со значением `on`. Метка сборки — 8 знаков коммита.
- **Угроза.** Взломанная зависимость сборки может испортить сайт через артефакт, но ключа Vercel не увидит.

## Разовая настройка (владелец)

1. **Vercel:** vercel.com → Sign Up → Hobby → по почте, не через GitHub: Vercel не нужен доступ к репозиторию. Account Settings → Authentication → Two-Factor Authentication — включить.
2. **Токен:** Account Settings → Tokens → Create Token. Имя `github-actions-site`, Scope — ваша команда («…'s projects»), Expiration — 1 year. Токен сразу кладите в секрет (шаг 3), не в чат и не в файлы. Слаг команды — из адреса `vercel.com/<слаг>`.
3. **GitHub, окружение:** Settings → Environments → New environment `site`. Deployment branches and tags: Selected branches → `main`; обход администратором — выключен. Environment secrets → `VERCEL_TOKEN`. Environment variables → `VERCEL_SCOPE` = слаг команды.
4. **GitHub, переменная:** Settings → Secrets and variables → Actions → Variables → New repository variable `SITE_DEPLOY` = `on`.
5. **Первая выкладка:** Actions → «Сайт» → Run workflow (main). «Выкладка» создаст проект `iconavo-site` и выложит сайт на адрес вида `iconavo-site.vercel.app` (он будет в сводке запуска). «Проверка» пока будет красной: домена ещё нет.
6. **Домен:** Vercel → iconavo-site → Settings → Domains → Add `iconavo.dev`. Основной адрес — `iconavo.dev`.
   - У карточки `iconavo.dev` — окружение **Production**.
   - У карточки `www.iconavo.dev` — **Redirect** на `iconavo.dev` (308).

   Vercel может предложить и обратное — `iconavo.dev` → `www`, так случилось 29 октября 2026. Тогда **Edit** у обеих карточек. Значения записей — с карточек доменов.
7. **Cloudflare:** зона `iconavo.dev` → DNS → Records → Add record. Записи — те, что на карточках Vercel. На 29 октября 2026 Vercel рекомендует для обоих имён одну цель вида `…vercel-dns-017.com`:
   - `CNAME`, Name `@`, Target — с карточки, Proxy status — **DNS only**. CNAME на корне домена Cloudflare разрешает: он сам заменяет её адресами (CNAME flattening);
   - `CNAME`, Name `www`, Target — с карточки, **DNS only**.

   Прежние записи Vercel — `A 76.76.21.21` и `CNAME cname.vercel-dns.com` — по его словам, тоже работают. AAAA не добавлять. Записи CAA в зоне нет (проверено 29 октября 2026), поэтому Let's Encrypt разрешён.
8. Дождаться «Valid Configuration» на карточке домена в Vercel.
9. Actions → «Сайт» → Run workflow: «Сборка», «Выкладка» и «Проверка» зелёные, https://iconavo.dev/docs открывается.

Не трогать:
- Settings → Git — репозиторий не подключать;
- Deployment Protection — оставить по умолчанию;
- Web Analytics и Speed Insights — оставить выключенными.

Уточнение от 29 октября 2026 (шаг 11 фазы 3, решение владельца): у документации третий источник — журнал изменений пакетов `packages/icon/CHANGELOG.md`, весь на странице `/docs/changelog` «Changelog» (ADR-0051). Разделы журнала — версии; их проверяют те же правила, что разделы README: каждый — на своей странице, ссылки и якоря — на месте.

Уточнение от 30 октября 2026 (шаг 1 фазы 4) — сайт стал каркасом каталога:

- **Страницы:** `/` и `/ru`, заглушки поиска `/search` и `/ru/search` (выдача — шаг 3), документация `/docs/*` — только на английском. Языки — две корневые раскладки `app/(en)` и `app/(ru)`. Несуществующие адреса отдаёт общая страница 404 `app/global-not-found.tsx`, а `/ru/docs…` временно (307) перенаправляют на английскую документацию (ADR-0037).
- **Общее у раскладок** — `components/Shell.tsx`: ссылка «к содержимому» первой в документе, шапка (`Header`: поиск, документация, GitHub, язык, тема), подвал, IconavoProvider. Тексты — `lib/i18n.ts`, метаданные — `lib/metadata.ts`, тема — `lib/theme.ts` (ADR-0038).
- **`pnpm site --check`:**
  - дополнительные адреса обхода — `CRAWL_EXTRAS` в `packages/pipeline/src/site/config.ts`, общий для `--check` и `--live`: три несуществующих, два перехода, две страницы поиска и `robots.txt`;
  - коды ответов — одна чистая функция `statusVerdict`: страницы — 200, несуществующие — 404, переходы — 307 на нужный адрес. У перехода заголовков сайта нет, поэтому строка заголовков их не смотрит;
  - новые строки: язык страницы (`<html lang>` по адресу), переключатель языка (ссылка на пару страницы с `hreflang`), поиск в шапке (форма ведёт на поиск своего языка), меню темы;
  - меню темы проверяется только с клавиатуры, в своём контексте на каждую тему системы: светлая → тёмная → как в системе. Фон должен меняться, тема — стоять до появления `<body>` после перезагрузки, Esc и выбор — возвращать фокус на кнопку. Открытое меню не добавляет `<style>`, не нарушает CSP и проходит axe в обеих темах;
  - «к содержимому» — на `/docs` и `/ru`, на языке страницы;
  - снимки — ещё `/ru` в двух темах и на телефоне и открытое меню темы;
  - контрольный запуск — одиннадцать поломок. К прежним семи добавлены страница `/ru/…` с `lang="en"`, страница без ссылки на другой язык, переход `/ru/docs` с кодом 308 на `/ru` и главная без скрипта темы (через `page.route`).
- **`pnpm site --live`** — те же строки по HTTP: коды и переходы, язык, переключатель, поиск в шапке.
- **Storybook** — `pnpm storybook`, витрина компонентов сайта на 127.0.0.1:6006 (ADR-0038).

Уточнение от 30 октября 2026 (шаг 2 фазы 4) — каталог наборов (ADR-0037, ADR-0039):

- **Данные — из edge API при сборке**, а не из `data/`: сайт показывает ровно то, что уже выложено на раздачу, те же адреса нужны MCP, а функциям сайта на Vercel до `data/` не дотянуться. Адрес — `NEXT_PUBLIC_ICONAVO_API` (его задаёт только `pnpm site --check`) или `https://api.iconavo.dev`; код — `apps/site/lib/catalog.ts`. Ответы запоминаются в памяти процесса сборки, чтобы большой набор не скачивался трижды; кэш данных Next.js не нужен — он пережил бы сборку на диске. Ответ не по формату или API не ответил — ошибка сборки, как у иконок сайта.
- **Иконки страниц** — образцы наборов, первая страница сетки и превью ленты — грузятся `loadIcons` при сборке во вложенный `IconavoProvider` (`loadPageIcons` в `lib/icons.ts`): они в серверном HTML, без мигания. Не загрузилась хоть одна — ошибка сборки.
- **В браузере** сетка набора один раз берёт список имён у `/collection` edge API, а иконки других страниц грузит ядро пакета. Ядро браузера настраивает `lib/iconavo.ts` — его импортирует сетка, как кнопка Copy.
- **Числа и даты** — `Intl` по языку страницы, время — по UTC; формы слов («1 998 иконок») — `Intl.PluralRules`. Считает сервер, в клиентские компоненты строки приходят готовыми — разметка не расходится при гидратации.
- **`pnpm site --check`:**
  - несуществующие адреса — ещё `/no-such-set`, `/ru/no-such-set` и адрес из трёх частей для общей страницы 404;
  - новая строка в браузерах «Каталог»: `/lucide` — первая страница из серверного HTML, страница 2, категория автора, «назад» и ссылка сразу на страницу 3. Адрес, имена по порядку и нарисованные иконки сверяются с `/collection` превью API; на `/sets` фильтр «цветные» оставляет столько карточек, сколько цветных наборов в `/collections`; метка версии на странице набора — как `X-Iconavo-Version` у API;
  - контрольный запуск — двенадцать поломок: браузер не получает список имён набора (`page.route` обрывает `/collection`), и сценарий обязан это заметить.

  Первым же прогоном строка «Каталог» нашла настоящую ошибку: ядро браузера не было настроено, и сетка просила иконки у хостов по умолчанию мимо CSP проверки.
- **`pnpm site --live`** — строка «Свежесть данных»: у страницы каждого набора из живого манифеста `cdn.iconavo.dev`, на обоих языках, метка `<meta name="iconavo-version">` — версия набора в манифесте. Иначе сайт собран со старыми данными.
- **Пересборка после «Выкладки»** — запуск `workflow_run` workflow «Сайт» (ADR-0039): только после успешной «Выкладки» в этом репозитории от push или ручного запуска на `main`, как у поискового индекса (ADR-0049). Запуск, который задача «Сборка» пропустит, идёт в своей группе очереди и ждущую выкладку не отменяет. Собирается свежий `main`. Ручной показ «Выкладки» тоже пересобирает сайт: признака показа в событии нет, а лишняя выкладка того же сайта безвредна.

Уточнение от 2 ноября 2026 (шаг 4 фазы 4, ADR-0041) — панель и страницы иконок в проверке сайта:

- **Предел обхода** (пункт бэклога).
  - Обход открывает только страницы иконок из списка `CRAWL_ICONS` (`src/site/config.ts`), на двух языках:
    - `lucide:house`;
    - `ph:house-bold`;
    - `tabler:home-filled`;
    - `material-symbols:home-outline-rounded`;
    - `fluent-emoji-flat:waving-hand`;
    - скрытая `lucide:circle-parking`.

    Плюс переход старого имени `/lucide/home` (308) и несуществующая иконка (404).
  - Остальные ссылки на иконки `linksVerdict` проверяет по форме адреса — `isIconPath`.
  - Иначе обход ушёл бы по карточкам, вариантам и похожим на десятки тысяч страниц.
- **Правка вердиктов:**
  - у переходов — свой код на адрес: 307 у `/ru/docs…`, 308 у старых имён иконок;
  - «Статичность»: страницы иконок — не в списке собранных заранее, а маршруты `/[prefix]/[icon]` и `/ru/[prefix]/[icon]` — в `dynamicRoutes` с `fallback: null`, повторный запрос — `x-nextjs-cache: HIT`.
- **Новые строки** (`src/site/panel.ts`), перед «Каталогом»:
  - **«Панель»** — на `/lucide` мышью и с клавиатуры:
    - адрес и запись истории;
    - фокус на заголовок и обратно к карточке;
    - смена иконки без новой записи;
    - Esc, ✕ и «назад»;
    - ссылка с `?icon=`.

    На `/ph`: варианты по таблице стилей, вариант и похожая открываются в панели, «Заливка» при открытой панели и ✕ после неё, нет толщины линии. У Fluent нет выбора цвета. axe с открытой панелью — в обеих темах.
  - **«Страница иконки»:**
    - серверный HTML двенадцати страниц из `CRAWL_ICONS`: заголовок, превью, метка версии;
    - «Устарела» на двух языках;
    - настройки из адреса;
    - «Открыть страницу иконки» из панели переносит поворот.
  - **«Телефон»** — 375 px:
    - шторка `fixed` не выше 60% экрана;
    - карточка над шторкой меняет иконку;
    - «развернуть» — с верха экрана;
    - «назад» закрывает;
    - нет прокрутки вбок.
- **Контрольный запуск** — плюс четыре поломки, всего семнадцать:
  - Esc перехвачен до панели;
  - фокус не возвращается к карточке;
  - смена фильтра выбрасывает `icon` из адреса;
  - старое имя иконки отвечает 200.
- **Превью API** проверки отвечает на `/icon`: локальный Meilisearch отдаёт `about` и похожих по общим словам.

Уточнение от 2 ноября 2026 (шаг 4 фазы 4, ADR-0039, ADR-0041) — сброс кэша по наборам, мокапы и проверки:

- **Workflow «Сайт» — два пути.**
  - **Выкладка кода** — push в `main` и ручной запуск: «Сборка» → «Выкладка» → «Проверка», как раньше.
  - **Сброс по наборам** — после каждого «Поискового индекса» на `main` вместо пересборки после «Выкладки»: индекс идёт после «Выкладки», и новые страницы сразу получают свежие описания и похожие. Задачи:
    1. «Сверка с раздачей» — без ключей: пауза 2 минуты (edge API помнит версию индекса до 90 секунд), затем `pnpm site --refresh`;
    2. «Сброс кэша» — окружение `site`, без checkout: `vercel link --project iconavo-site` во временной папке и `vercel cache invalidate --tag catalog,set-{набор}…`, группами не больше 16 меток. Метки сверяются с правилом имён до команды с ключом;
    3. «Свежесть» — без ключей: `pnpm site --refresh --wait=300 --since=… --sets=…`, затем `pnpm site --live`;
    4. «Пересборка» — только если у набора нет страницы (новый набор): право `actions: write`, без checkout, запускает обычную выкладку этого workflow, и та встаёт в общую очередь выкладок.
  - **Ручной запуск:** «только сброс» или «сбросить все наборы» (проба сброса). «Только показ» — сравнить без сброса.
  - **Защита.** Условие после индекса — этот репозиторий, `main`, индекс закончился удачно или с ошибкой (не пропущен и не отменён), событие индекса — push, ручной запуск или `workflow_run` после «Выкладки». Запуск из форка — событие `pull_request` из чужого репозитория, он не проходит. Задача сверки только читает открытые адреса, сбрасывает она лишь то, что расходится с раздачей. Неудачный индекс сайт не держит.
  - **Очереди.** У сбросов своя очередь `site-refresh`: в общей новый сброс отменил бы ждущую выкладку кода — у очереди одно место для ждущего. Сброс во время выкладки безвреден: новая выкладка и так начинает с пустого кэша.
- **`pnpm site --refresh`** (`src/site/refresh.ts`) — только открытые адреса:
  - отпечаток каждого набора на его странице на обоих языках (`iconavo-content`) сравнивается с оглавлением каталога раздачи (`cdn.iconavo.dev/manifest.json` → `catalog/{хэш}.json`);
  - итог — `.cache/reports/site/refresh.json`: устаревшие, без страницы (новые) и группы меток для сброса; `--all` — все наборы со страницей устаревшие;
  - `--wait=N --since=… --sets=…` — ждать до N секунд, пока страницы этих наборов на обоих языках и страница первой иконки витрины покажут отпечаток из каталога; с `--all` — ещё и время сборки (`iconavo-rendered`) не раньше сброса, с допуском 10 секунд на часы. Опрос — раз в 10 секунд: первый ответ после сброса — прежняя страница.
- **`pnpm site --check`:**
  - новая строка **«Метки кэша»**: у главной, `/sets` и `/ru/licenses` — ровно `catalog`, у `/lucide`, `/ru/lucide`, `/lucide/house` и `/ru/ph/house-bold` — ровно `set-{набор}`. Метки — из файлов кэша Next.js: собранные заранее страницы — `.next/server/app/{путь}.meta`, страницы по первому запросу next start 16.4 — `.next/server/route-cache/APP_PAGE/{хэш}/$/{путь}.meta`;
  - «Страница иконки» — ещё и мокапы: восемь мест и шестнадцать панелей тем в серверном HTML; в браузере всё нарисовано, у двух тем разный фон, цвет из адреса у выбранной иконки, в кнопке — 20 px, а не размер превью, панели скрыты от экранных дикторов;
  - «Серверный HTML» не считает заглушки мокапов, как и похожих: их рисунки догружает браузер;
  - контрольный запуск — восемнадцать поломок, новая — метка `catalog` у страницы иконки.
- **`pnpm site --live`** — две новые строки:
  - «Отпечатки содержимого» — страницы наборов на двух языках и страницы иконок выборки против оглавления каталога раздачи;
  - «Страницы иконок» — заголовок, превью, метки и мокапы выборки, «Устарела» у скрытой. Тот же разбор (`iconPagesProblems`) у строки «Страница иконки» проверки сайта.

Почему: разработчик выбирает библиотеку за несколько минут. Документация с одной точкой входа на нашем домене и примеры, которые открываются по ссылке, дают эти минуты, а единый источник — README — не даёт сайту и npm разойтись.
