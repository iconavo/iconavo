# ADR-0049. Поисковый сервис: реализация

Статус: принято 26 октября 2026. Решения владельца — регион, тариф, Polza для векторов запросов, закрытый бакет, векторы иконок в бакете, правило приёмки качества; остальное — по рекомендации. Правила замера записаны до замера — в первом PR шага 8 фазы 2, как в ADR-0048.

Вопрос: как прототип поиска шага 12 (ADR-0048) становится сервисом для сайта, пакета и MCP (ADR-0027) — быстрым (ADR-0040) и не хуже прототипа по эталону (ADR-0021)?

## Решение

### Сервис и индекс

- **Meilisearch Cloud во Франкфурте** (решение владельца): ближе всего к России и Европе. После 14 дней пробы — тариф по ресурсам XS, ≈ $23 в месяц: 0,5 vCPU, 1 ГБ памяти, без лимита на число поисков. Если индексу не хватит памяти — размер S, ≈ $41.
- **Индекс `icons`**: документ — карточка, как у прототипа. Карточка — базовая иконка со своими вариантами; оттенки кожи Fluent — одна карточка (ADR-0048). На 26 октября 2026 это 14 126 карточек.
  - **Поиск по словам** — поля `name`, `tags`, `synonymsEn`, `synonymsRu` в этом порядке. В `name` — имя и прежние имена (алиасы-переименования).
    - Слова идут фразами, как в файлах набора, нормализованные так же, как запрос (ниже).
    - Описания в поиск по словам не идут, только в вектор (решение шага 12).
  - **Фильтры**:
    - `set` — набор;
    - `palette` — цветность;
    - `license` — SPDX;
    - `names` — точное имя.

    Стиль — в фазе 4: у наборов разные названия стилей (Regular у Material Symbols — заливка, у Phosphor — обычная линия), нужна общая шкала.
  - **Порядок** — правила Meilisearch по умолчанию. При равенстве — короткое имя (`parts`), порядок наборов в реестре (`setOrder`) и имя по алфавиту, как у прототипа. Место иконки внутри набора не хранится: новая иконка сдвигала бы его у всех следующих, и они уходили бы в индекс заново.
  - **Служебные слова** — тот же список, что у прототипа; он переехал в общий модуль. **Опечатки** — как у Meilisearch по умолчанию: одна от 5 букв, две от 9.
  - **Эмбеддер** `gemini`, `userProvided`, длина 1024: векторы считаем сами (ADR-0010, ADR-0048).
  - **id документа** — `{набор}_{имя}`: двоеточие в id Meilisearch нельзя, а `_` нет ни в наборах, ни в именах.
- **Общий модуль `packages/search`** (`@iconavo-ui/search`) — то, что робот индекса, замер и функция edge API обязаны считать одинаково:
  - нормализация запроса;
  - ключ вектора;
  - настройки индекса;
  - тела запросов к Meilisearch;
  - страницы выдачи.

  Это отдельный пакет, а не часть `core`: ядро уходит в npm в фазе 3, и поисковые настройки в нём стали бы публичным API.

### Нормализация и точное имя

- **Текст запроса** для вектора и поиска по словам:
  - NFC;
  - управляющие символы — пробелы;
  - строчные буквы, ё→е;
  - дефисы, подчёркивания и пробелы — один пробел.

  «Shopping-Cart» и «shopping cart» дают один вектор, «Ёлка» и «елка» — одну фразу каталога.
- **Префикс `набор:`** известного набора словом не ищется: `lucide:house` ищет `house`. Ошибка прототипа исправлена: в его выражении стояло `^s*` вместо `^\s*`.
- **Точное имя первым** (ADR-0009, ADR-0040): запрос в виде имени по ADR-0001 (`house`, `lucide:house`) — отдельный запрос с фильтром `names = "…"`. Основная выдача его карточки исключает (`NOT names = "…"`) и берётся окном с запасом в 50 позиций: страницы идут без пропусков и повторов.

### Векторы

- **Модель** — `google/gemini-embedding-001` через Polza (решение владельца, ADR-0010). Векторы иконок — те же, что у прототипа: полный вектор, первые 1024 числа, снова длины 1.
  - Polza с `dimensions: 1024` отдаёт тот же вектор без нормировки: проба 26 октября 2026, косинус 1,000000.
  - Функция будет просить сразу 1024 числа — ответ втрое короче.
- **Закрытый бакет R2 `iconavo-search`** без публичного адреса, со своим ключом (решение владельца). Робот поиска не получает ключ записи от раздачи. В бакете:
  - `icons/gemini-1024/{набор}.f32` и `.json` — векторы иконок, формат как в `.cache/embeddings` (ADR-0047). Векторы иконок теперь и здесь — уточнение к ADR-0047, решение владельца; в git их по-прежнему нет. Так индекс пересобирается без Polza и без компьютера владельца;
  - `phrases/gemini-1024/{хэш}.f32` — векторы фраз каталога заранее (ADR-0040): имена, теги, синонимы ru/en и отдельные слова из них. Это 68 468 фраз, без служебных и однобуквенных слов;
  - `index.json` — версия индекса.
- **Ключ вектора** — первые 32 символа SHA-256 от id модели и нормализованного текста, через WebCrypto. Робот и функция считают его одинаково — это проверяет эталонный тест.

### Робот индекса

- **Команда** — `pnpm search-index [--dry-run] [--max-rub=N] [--reembed]` (код — `packages/pipeline/src/meili/`). Порядок:
  1. Карточки из `data/`.
  2. Сверка версий наборов с живым манифестом `cdn.iconavo.dev`: расхождение — «СТОП». В поиске не появляются иконки, которых ещё нет на раздаче.
  3. Векторы иконок из бакета. Недостающие (новый текст) считает Polza, набор записывается в бакет целиком: векторы, затем оглавление.
  4. Настройки индекса — только если отличаются. Смена эмбеддера стирает векторы, поэтому без `--reembed` — «СТОП».
  5. Документы — только изменившиеся по отпечатку; лишние удаляются (скрытые иконки, пропавшие карточки).
  6. `index.json` с версией индекса — сразу после документов. Версия — 8 символов SHA-256 от настроек и отпечатков документов.
  7. Недостающие векторы фраз — объект на фразу, дозапись продолжается после обрыва.
- **Стоимость** — оценка до отправки, лимит `--max-rub` (по умолчанию 60 ₽). Первый запуск с нуля по оценке — 52,79 ₽ с запасом; по опыту ADR-0047 — ≈ 34 ₽ на иконки и ≈ 5 ₽ на фразы.
- **Без ключей** `--dry-run` — план с нуля без сети; с ключом только для чтения — сравнение с индексом и бакетом без записи.
- **Workflow «Поисковый индекс»** (`.github/workflows/search.yml`):
  - запускается после каждой успешной «Выкладки» на main (ровно тот коммит, что выложен), при изменении кода поиска в main и вручную — «только показ» и «сменить эмбеддер»;
  - окружение `search` (только main);
  - замер сервиса «только отчёт» — `pnpm eval --service-only`: судьи в CI нет, неразмеченные пары — заметка. Это выполняет обещание ADR-0021 перенести замер в CI в фазе 2, для сервиса.

### Замер качества

- **Варианты:**
  - «Сервис» — гибрид Meilisearch теми же запросами, что у функции;
  - «Сервис, только слова» — выдача «сначала текст»;
  - сетка доли смысла 0…1 с шагом 0,1.

  Код — `packages/pipeline/src/eval/service.ts`; флаги `pnpm judge --service`, `pnpm eval --service | --service-only`.
- **Новые пары** размечает тот же судья (ADR-0048). Сумму — заранее, с согласия владельца.

**Правила записаны до замера** (26 октября 2026):

1. **Доля смысла (`semanticRatio`)** — по рабочей части, по тому же правилу, что α прототипа (`pickAlpha`): середина лучшего плато по Hit@5, при равенстве — по MRR@10. Подбирается, только когда первые десятки всей сетки на рабочей части размечены целиком.
2. **Приёмка качества** (решение владельца) — сервис не хуже гибрида Gemini прототипа (`hybrid:gemini`) на контрольной части:
   - либо Hit@5 не ниже;
   - либо разница в пределах случайности — точный тест Мак-Немара, p ≥ 0,05.

   Русские и английские запросы и строгий Hit@5 — рядом, для справки.
3. **Запасной способ** — только если сервис хуже прототипа сверх случайности (p < 0,05). По порядку, каждый шаг — с новым замером; контрольная часть не разглядывается:
   1. калибровка шкалы смысла (`distribution` эмбеддера) по смысловым оценкам рабочей части и подбор доли заново;
   2. слияние в функции по формуле прототипа: два списка Meilisearch — только слова и только смысл — и выпуклая сумма.
4. **Протокол скорости** (часть 2 шага 8):
   - запросы — 100 запросов контрольной части к живому `/search`;
   - проход «холодный»: новая сборка функции — новые ключи кэша; не больше 50 запросов в минуту (лимит — 60);
   - мера — время до первого ответа, полного или `pending`; цель — 95% не дольше 0,3 с (ADR-0040) с машины GitHub;
   - для справки — с компьютера владельца, доля полных ответов и время до полной выдачи.

## Проверено 26 октября 2026 — проба на временном индексе

- **Meilisearch 1.55.0** во Франкфурте принимает настройки индекса, включая порядок по строке (`icon:asc`). Сравнение настроек робота с тем, что отдаёт Meilisearch, — без отличий.
- **Гибрид:**
  - запрос «слова + вектор + доля смысла» работает: «корзина» находит обе корзины, опечатка «корзна» — тоже;
  - ответ не повторяет вектор запроса — для 10 мс процессора бесплатного Workers это важно;
  - документы без вектора (`null`) в смысловой части — последними.
- **multi-search:**
  - точное имя фильтром `names` — две карточки `house` впереди, основная выдача без них;
  - `lucide:home` с фильтрами набора, цветности и лицензии находит `lucide:house` через алиас.
- **Время с компьютера владельца:**
  - ответ Meilisearch по уже открытому соединению — 90 мс;
  - новое защищённое соединение — 5–16 с, как и с другими хостами (сеть владельца);
  - вектор запроса через Polza — 1,4–1,8 с.

  Скорость с серверов Cloudflare меряется в части 2.
- **Ключи:**
  - ключ бакета `iconavo-search` пишет, читает и удаляет;
  - ключ Meilisearch только для чтения на запись получает 403.
- **Без ключей** план — 14 126 карточек и 68 468 фраз. С ключами показ сошёлся с манифестом раздачи по всем пяти наборам.

## Почему

Индекс повторяет карточки прототипа, а замер идёт теми же запросами, что у функции. Поэтому цифры сервиса сравнимы с `baseline.json`, а правила, записанные до замера, не дают подогнать долю смысла под контрольную часть. Векторы в закрытом бакете делают индекс воспроизводимым без компьютера владельца, а сверка с манифестом не даёт поиску обогнать раздачу.

## Последствия

- Сайту с серверным рендером и MCP (фаза 4) понадобится ключ или обход лимита частоты по IP: решить вместе с ними.
- Новые наборы (фаза 5) увеличат индекс: размер тарифа — по замеру памяти.
- Робот обновления векторы не считает — после слияния его PR их досчитает «Поисковый индекс» после «Выкладки». А `pnpm enrich` по-прежнему запускается вручную.
