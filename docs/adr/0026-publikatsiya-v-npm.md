# ADR-0026. Публикация в npm

Статус: принято 16 октября 2026 по рекомендации, с опорой на Iconify.

Вопрос: как устроены пакеты данных и как их безопасно публиковать?

Решение:

- Один пакет на набор: `@iconavo-ui/icons-{префикс}`. У Iconify так же: один набор — один пакет.
- Внутри — `icons.json`, `info.json`, `metadata.json`, лицензия автора набора, файл NOTICE (если есть) и README. Данные поиска из `search.json` в пакет не входят.
- Поле `exports` и типы TypeScript, чтобы файлы подключались одной строкой.
- Публикация — только из GitHub Actions через доверенную публикацию (trusted publishing) с подписью provenance. Личных токенов нет, на аккаунте npm включена двухфакторная аутентификация.
- Публикуются только изменившиеся наборы, версии — по ADR-0005.
- До запуска пакеты выходят под тегом `next`, в день запуска — под `latest`.

Уточнение от 23 октября 2026 (шаг 5 фазы 2, пакеты данных):

- **Пакет.** Папка `dist-npm/{набор}/` — в корне репозитория, в git не попадает, как `dist-cdn/`.
  - `icons.json`, `info.json`, `metadata.json` — побайтные копии из `data/{набор}/`.
  - `LICENSE` и `NOTICE` — `NOTICE`, только если он есть у автора.
  - `index.js` — ES-модуль: три JSON через `import … with { type: "json" }`, как у Iconify. Только ESM, как у пакетов для разработчиков (ADR-0034).
  - `index.d.ts` — типы без зависимостей; `prefix` — точное имя набора.
  - `README.md` — на английском (решение владельца 23 октября 2026): установка с тегом, пример, что внутри, автор и лицензия, версия набора.
  - `package.json`.

  `search.json` и `CHANGELOG.md` в пакет не входят. Подключение одной строкой — `import { icons } from "@iconavo-ui/icons-lucide"` или один файл `@iconavo-ui/icons-lucide/icons.json`.
- **Поля `package.json`.**
  - `license` — SPDX набора.
  - `repository` — `git+https://github.com/iconavo/iconavo.git` с `directory: data/{набор}`: этот адрес npm сверяет с подписью provenance.
  - `exports` — `.`, три JSON и `package.json`; у `.` условие `types` — первым. Остальные файлы, в том числе `search.json`, если бы он попал в папку, снаружи не открываются.
  - `files` — явный список. Файлы, как их упакует npm (`npm pack --dry-run`), CI сверяет с планом.
  - `publishConfig` — `{ access: public, provenance: true, tag: next }`.
  - `iconavo` — `{ set, setVersion, fingerprint }`: набор, его версия (ADR-0018) и отпечаток содержимого. Реестр отдаёт эти поля в описании пакета без скачивания архива.
  - Нет `scripts` и зависимостей: при публикации и установке не запускается ничего. Нет `homepage`, пока нет сайта.

  Поля пишутся в постоянном порядке, без сортировки ключей: в `exports` важен порядок условий.
- **Версии** (ADR-0005; решение владельца 23 октября 2026 — начинать с 1.0.0).
  - Отпечаток — SHA-256 всех файлов пакета и `package.json` без номера версии и без самого отпечатка. Тег тоже входит в отпечаток.
  - Сравнение — с версией под тегом `next`, а нет тега — со старшей живой версией. Номер — от самой старшей когда-либо вышедшей версии, даже снятой: npm не даёт занять номер повторно.

  | Что изменилось | Версия |
  | --- | --- |
  | Пакета ещё нет | `1.0.0`, только при ручном запуске с «первой публикацией» |
  | Отпечаток тот же | не публикуется |
  | Появились новые имена — иконки или алиасы | средняя цифра |
  | Другое: рисунки, скрытия, метаданные, README | последняя цифра |
  | Константа `NPM_FORMAT_MAJOR` больше первой цифры в npm | первая цифра: `N.0.0` |

  Новые имена ищутся по архиву опубликованной версии. SHA-512 архива проверяется до распаковки, а адрес архива должен быть из реестра.

  «СТОП» — ни один пакет не публикуется, `plan.json` не пишется:
  - имя из опубликованной версии пропало (ADR-0005);
  - версии набора из npm нет в `changelog.json` этой сборки: в npm данные новее, и старая сборка не откатит пакет;
  - у версии в npm нет отметки `iconavo`: её выложил не конвейер;
  - первая цифра в npm больше `NPM_FORMAT_MAJOR`;
  - набор не читается или не по схеме.

  `--force` выпускает последнюю цифру и без изменений: так проверяется доверенная публикация в те самые 2 дня (ниже).
- **Команды.**
  - `pnpm packages prepare [набор…] [--new] [--force]` — папки пакетов и план для CI `dist-npm/plan.json`: по каждому пакету действие, версия, базовая версия в npm, публиковать ли и список файлов.
    - Реестр только читается, ключи не нужны; сама команда ничего не публикует.
    - Без `--new` новый пакет — «ждёт первой публикации», это не ошибка.
    - Повтор без изменений не пишет ни байта.
    - Отчёт — `.cache/reports/npm/index.html`: решение, новые имена, файлы с размерами, `package.json` и README.
  - `pnpm packages verify [набор…] [--wait=N]` — пакеты собираются заново из `data/` и сверяются с реестром:
    - под тегом — версия с тем же отпечатком: ждёт до N секунд, пока реестр её покажет;
    - архив побайтно равен сборке;
    - подпись provenance (SLSA v1) из `https://github.com/iconavo/iconavo`, `.github/workflows/publish.yml`, `refs/heads/main`, и подписан именно этот архив;
    - выложено доверенной публикацией: в реестре у версии есть `_npmUser.trustedPublisher`. Токен допустим только у самой первой версии пакета.

    `latest` — только для сведения; пакета ещё нет — предупреждение. Отчёт — `.cache/reports/npm/verify.html`.
  - Код — `packages/pipeline/src/npm/`, общая часть чтения набора с раздачей — `loadSetData` в `src/cdn/load.ts`.
- **Workflow «Публикация в npm»** (`.github/workflows/publish.yml`).
  - Запуски:
    - `push` в `main` при изменении `data/**`, кода `src/npm/` или самого workflow;
    - раз в сутки в 06:37 UTC — доопубликовать недошедшее и проверить; письмо GitHub о неудачном запуске по расписанию — оповещение, как у «Сверки хостов»;
    - вручную — поля «наборы», «первая публикация новых пакетов», «новая версия без изменений», «только показ»;
    - на PR, который меняет `src/npm/` или workflow, — только показ.
  - Публикует только «живой» запуск: ветка `main`, не PR и не «только показ», и `main` за это время не ушёл вперёд по `data/` и коду. Остальные — только показ.
  - Задачи:
    1. «Подготовка» — права только на чтение. Шаги:
       - `pnpm packages prepare`, ручной запуск с «первой публикацией» добавляет `--new`;
       - сверка списка файлов с `npm pack --dry-run`;
       - папка `dist-npm` — артефакт, отчёт — страница, таблица — в сводке запуска.
    2. «Публикация» — окружение GitHub `npm` и право только `id-token: write`.
       - Ни checkout, ни `pnpm install`: там, где можно публиковать, не работает ничей код, кроме npm, который идёт с Node 24 (нужен 11.5.1 и новее, проверяется).
       - Перед каждым пакетом — реестр ещё раз. Версия уже вышла — пропуск: повтор запуска не сломается. Под тегом не та версия, от которой считал план, — «план устарел», пакет не публикуется.
       - Новый пакет без токена — ошибка с подсказкой.
       - Затем `npm publish ./dist-npm/{набор} --tag next --access public --provenance --ignore-scripts`.
       - `NODE_AUTH_TOKEN` подставляется, только если есть секрет `NPM_TOKEN`: пустое значение мешает доверенной публикации.
    3. «Проверка» — `pnpm packages verify` на каждом «живом» запуске, и после неудачной публикации тоже. Ожидание реестра: 10 минут после публикации, 2 — после сбоя, 0 — если публиковать было нечего.
  - Публикации из `main` идут по одной (группа `publish`) и не прерываются. Показы с веток и PR — в своих группах: в общей они отменяли бы ждущую публикацию. Свежий запуск отменяет ждущий в очереди — ручной запуск в этом случае нужно повторить.
  - **Не переименовывайте `publish.yml` и окружение `npm`:** к ним привязана доверенная публикация на npmjs.com, а её поля после создания не меняются.
- **Без одобрения каждой версии** (решение владельца 23 октября 2026). С 3 сентября 2026 npm по умолчанию разрешает доверенной публикации только `npm stage publish`: версия ждёт, пока сопровождающий подтвердит её на npmjs.com с 2FA.
  - Здесь CI публикует сам, как выкладка на CDN: данные обновляются несколько раз в неделю, а неподтверждённые версии CI не видит — `npm stage list` требует входа человека.
  - Защита — публикация только из `main` (защищённой ветки, ADR-0036), окружение `npm`, задача без чужого кода, provenance и проверка после публикации.
  - Решить перед запуском, нужно ли одобрение (бэклог). Человеческий шаг можно добавить и без npm: обязательные проверяющие у окружения `npm`.
- **Настройки — ставит владелец; дословно.**
  - GitHub, окружение `npm` (создано 23 октября 2026 через `gh api` по решению владельца): Settings → Environments → `npm` → Deployment branches and tags: Selected branches → `main`; обход администратором выключен. Секрет окружения `NPM_TOKEN` — только на время первой публикации нового пакета.
  - npm: двухфакторная защита аккаунта включена; владелец — owner организации `iconavo-ui`.
  - Временный токен первой публикации: npmjs.com → аватар → Access Tokens → Generate New Token.
    - Expiration — самый короткий срок (не меньше суток).
    - Bypass two-factor authentication ✓.
    - Allowed IP Ranges — пусто: адреса машин GitHub меняются.
    - Packages and scopes — Permissions «Read and write (publish and stage)», Only select packages and scopes → `@iconavo-ui`.
    - Organizations — No access.

    Токен — сразу в секрет окружения, не в чат и не в файлы. После первой публикации секрет удаляется, а токен отзывается на той же странице.
  - Доверенная публикация, у каждого пакета: npmjs.com → пакет → Settings → Trusted Publisher → GitHub Actions.
    - Organization or user — `iconavo`;
    - Repository — `iconavo`;
    - Workflow filename — `publish.yml`;
    - Environment name — `npm`;
    - Allowed actions — ✓ npm publish; npm dist-tag не нужен.

    Новая настройка должна дождаться первой успешной публикации через неё **в течение 2 дней**, иначе истекает — тогда удалить и создать заново.
  - После этого у каждого пакета: Settings → Publishing access → «Require two-factor authentication and disallow tokens» → Update Package Settings. Доверенная публикация продолжает работать.
- **Первая версия нового пакета** — и для будущих наборов (фаза 5). Доверенную публикацию npm включает только у пакета, который уже есть в реестре, поэтому:
  1. Владелец создаёт временный токен и кладёт его в секрет `NPM_TOKEN` окружения `npm`.
  2. Ручной запуск «Публикации в npm» с наборами и «первой публикацией» ✓. Выходит `1.0.0` через токен, с provenance: в GitHub Actions npm подписывает и при токене.
  3. Владелец удаляет секрет и отзывает токен.
  4. Владелец включает доверенную публикацию у нового пакета.
  5. В течение 2 дней — ручной запуск с теми же наборами и «новой версией без изменений» ✓. Выходит `1.0.1` с тем же содержимым — уже доверенной публикацией: «Проверка» показывает «доверенная публикация».
  6. Владелец включает «Require two-factor authentication and disallow tokens».
- **Тег в день запуска.** `NPM_TAG` в `src/npm/config.ts` → `"latest"`. Тег входит в отпечаток, поэтому CI сам выпустит новую версию каждого пакета под `latest` через доверенную публикацию; права менять теги не нужны.

Почему: разработчик ставит ровно тот набор, который ему нужен, а подпись доказывает, что пакет собран в CI из конкретного коммита.
