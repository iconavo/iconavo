# ADR-0023. Заголовки и кэширование

Статус: принято 16 октября 2026 по рекомендации, с опорой на Iconify.

Вопрос: какие служебные заголовки отдаются, чтобы иконки грузились быстро, с любого сайта и безопасно?

| Что | Cache-Control | Почему |
| --- | --- | --- |
| Версионированная статика | `public, max-age=31536000, immutable` | Содержимое по адресу не меняется никогда |
| `manifest.json` | `public, max-age=300` | Новая версия видна через 5 минут |
| Ответы edge API | `public, max-age=604800` | Неделя, как у Iconify ([источник](https://iconify.design/docs/api/hosting-js/config.html)) |
| Поиск | `public, max-age=3600` | Часовой кэш популярных запросов |

- После каждого выпуска набора кэш edge API на CDN сбрасывается по этому набору: CDN сразу отдаёт свежие ответы, а в браузерах старые живут не дольше недели.
- CORS для всех источников, как у Iconify: `Access-Control-Allow-Origin: *`.
- Типы `application/json`, `image/svg+xml` и `text/css`; сжатие Brotli и gzip включает CDN.
- Для SVG — `X-Content-Type-Options: nosniff` и строгая политика безопасности: даже если открыть файл напрямую, код в нём не выполнится.

Уточнение от 22 октября 2026 (шаг 2 фазы 2): `Content-Type` и `Cache-Control` из таблицы задаются при выгрузке и хранятся у каждого объекта R2 (`pnpm cdn upload`, ADR-0022) — год и `immutable` у файлов версий, 5 минут у манифеста; типы — с `charset=utf-8`. Остальное — CORS, `X-Content-Type-Options`, политика безопасности для SVG, сжатие и правило кэша для JSON (со своего домена Cloudflare по умолчанию JSON не кэширует) — настройки Cloudflare, шаг 3.

Уточнение от 22 октября 2026 (шаг 3 фазы 2, правила Cloudflare и `pnpm cdn check`):

- **Что было до шага.** Тип файла, `Cache-Control` и сжатие `br` и `gzip` уже были верными. Не хватало трёх вещей:
  - CORS: заголовка не было даже на запрос с `Origin`;
  - защиты: `nosniff` и политики безопасности;
  - кэша JSON на CDN: `cf-cache-status: DYNAMIC`, SVG Cloudflare кэширует и сам.

  Ответ 404 приходил без CORS. Чужой сайт видел бы сбой сети вместо «иконки нет», а ядру фазы 3 нужно их различать, чтобы запоминать отсутствующие иконки (ADR-0030).
- **Три правила в зоне `iconavo.dev`.** Их ставит владелец в панели Cloudflare: Rules → Overview → Create rule. Новых ключей не нужно. Выражения вставляются через Edit expression.
  1. Cache Rule «Раздача: кэш по заголовкам файлов».
     - Выражение: `(http.host eq "cdn.iconavo.dev" and http.request.uri.path ne "/manifest.json")`.
     - Cache eligibility: Eligible for cache.
     - Edge TTL: Use cache-control header if present, bypass cache if not. CDN хранит файл по его `Cache-Control` — у версий это год, а ответ без заголовка (404) не хранит.
     - Browser TTL: Respect origin. Без этого настройка зоны Browser Cache TTL (по умолчанию 4 часа) заменяет более короткий `max-age` из ответа.
  2. Response Header Transform Rule «Раздача: CORS и защита».
     - Выражение: `(http.host eq "cdn.iconavo.dev")`.
     - Set static: `Access-Control-Allow-Origin: *`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: cross-origin`.
     - CORP нужен сайтам со строгой изоляцией (COEP): без него они не покажут наши SVG в `<img>`. Так отвечают и Iconify, jsDelivr, unpkg.
  3. Response Header Transform Rule «Раздача: CSP для SVG».
     - Выражение: `(http.host eq "cdn.iconavo.dev" and http.request.uri.path.extension eq "svg")`.
     - Set static: `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox` — как у GitHub для сырых файлов. Открытый напрямую SVG не выполнит код и ничего не загрузит.
     - Только SVG: JSON и так не исполняется, а `sandbox` может отключить встроенный просмотр JSON в браузере.
- **Почему CORS — правилом, а не настройкой CORS у бакета.** Бакет R2 ставит заголовок только на запрос с подходящим `Origin`. Копия в кэше CDN одна на всех: если первым придёт запрос без `Origin`, все получат копию без CORS. Правило заголовков работает после решения о кэше, поэтому меняет и ответы из кэша.
- **Манифест на CDN не кэшируется** (правило кэша его исключает), каждый запрос читает R2:
  - проверка после выкладки и мониторинг (ADR-0028) видят настоящий файл в бакете, а не копию;
  - новая версия видна в браузерах не позже чем через 5 минут;
  - запросов к манифесту мало: ядро читает его только в запасном режиме (ADR-0030).

  Если манифест кэшировать, 5 минут тоже сохранятся: Cloudflare отдаёт возраст копии в заголовке `Age`, и браузер учитывает его. Вернуться к этому вместе со сбросом кэша через API на шаге 7.
- **Предварительные запросы `OPTIONS` не поддерживаются** — ответ 403 от R2. Обычный GET без своих заголовков их не делает: так грузят ядро, `<img>` и CSS-маски. Если понадобится, добавить настройку CORS у бакета (бэклог).
- **Сжатие** Cloudflare делает сам и для ответов из кэша, отдельного правила нет.
  - Браузеру, который понимает `zstd` (Chrome), Cloudflare отдаёт `zstd`. Остальным — `br` или `gzip`, их и проверяет `pnpm cdn check`.
  - На обновление страницы браузер спрашивает, изменился ли файл, и получает `304` без тела. Заголовка сжатия в таком ответе нет, заголовки правил есть.
  - Оба случая проверены 22 октября 2026: владелец — в DevTools, повтором его запроса — через curl.
- **Проверка — `pnpm cdn check`.** Ключи не нужны, сборку команда не запускает. Она читает живые адреса: манифест, файл сумм и иконку `lucide:heart` (.json и .svg) текущей версии, плюс несуществующее имя `_missing` — «_» в именах запрещён (ADR-0001).
  - К каждому файлу два GET-запроса. Первый — с `Origin` и «br, gzip», как у чужого сайта. Второй — без `Origin`, только gzip.
  - Проверяется:
    - код ответа;
    - точные `Content-Type` и `Cache-Control`;
    - `cf-cache-status`: файлы версий — HIT, MISS и похожие, манифест — DYNAMIC или BYPASS;
    - CORS на обоих запросах;
    - `nosniff` и CORP, у SVG ещё CSP;
    - сжатие `br` и `gzip`, распакованные ответы одинаковые;
    - содержимое: схема манифеста и файла сумм, SHA-256 иконки по файлу сумм.
  - У 404 — только код, CORS и защита.
  - Перенаправление — неверный ответ. Сбой сети, ожидание 30 с и временные ответы повторяются до 3 раз.
  - Вывод — таблица «адрес × проверки», список «не так» с подсказкой, какое правило поправить, и итог. Код выхода 1 — есть проблемы.
  - Запускается и в «Выкладке» после выгрузки.
  - Константы — `packages/pipeline/src/cdn/config.ts`, код — `src/cdn/check.ts` и `check-report.ts`.
- Проверено 22 октября 2026, до правил: `pnpm cdn check` нашёл 18 проблем — CORS у всех пяти адресов, защиту, кэш JSON на CDN. Тип, `Cache-Control`, сжатие и содержимое — «ок». 9 запросов за 16 с с компьютера владельца: новое соединение с этой машины открывается до 10 с.
- Проверено 22 октября 2026, после правил: `pnpm cdn check` — «ок» у всех пяти адресов.
  - JSON версий отдаётся из кэша CDN: `cf-cache-status: HIT`, есть `Age`.
  - Манифест — `DYNAMIC`, `max-age=300`.
  - 404 — `BYPASS`, с CORS.
  - CSP только у SVG.

  В Chrome со страницы `https://example.com`:
  - `fetch` иконки — 200, несуществующей — 404, ошибки CORS нет;
  - `<img>` грузится с `crossorigin` и без;
  - CSS-маска `lucide:heart` рисуется;
  - SVG Fluent, открытые как документ с CSP (iframe и object), выглядят как в `<img>`: `airplane-arrival` с `clipPath` и `phoenix-bird` с градиентами. Ссылки `url(#…)` внутри файла политика не трогает.

Уточнение от 22 октября 2026 (шаг 4 фазы 2, второй хост):

- На `cdn2.iconavo.dev` заголовки те же. `Cache-Control` у файлов Bunny не хранит, а тип отдаёт по расширению без `charset`, поэтому их, CORS и защиту ставят шесть правил зоны CDN Bunny; дословно они записаны в ADR-0025. Сжатие Bunny делает сам.
- Манифест и там идёт мимо кэша CDN: перезапись в хранилище Bunny не сбрасывает копию в кэше.
- `pnpm cdn check` проверяет оба хоста по очереди, затем — что их манифесты побайтно одинаковые.
- Состояние кэша на Bunny показывает заголовок `CDN-Cache`.
- Новая проверка у обоих хостов: заголовок `Server` ответов файлов — от CDN этого хоста (`cloudflare` или `BunnyCDN`). Так видно, что запись `cdn2` не идёт через прокси Cloudflare.

Уточнение от 23 октября 2026 (переход на https, решение владельца):

- В зоне `iconavo.dev` включён Always Use HTTPS (SSL/TLS → Edge Certificates). `http://cdn.iconavo.dev/…` отвечает 301 на тот же адрес по https, путь и параметры сохраняются. Раньше файлы отдавались и по `http://` — по дороге иконку можно было подменить.
- Переход — для всей зоны, а не правилом только для `cdn`: других адресов в зоне через прокси Cloudflare нет (у корня домена записей нет, лендинг живёт не здесь), а будущим `api` и `mcp` тоже нужен только https.
- `cdn2.iconavo.dev` идёт мимо Cloudflare: там переход делает Force SSL у Bunny (ADR-0025), тоже 301.
- Браузеры и так открывают `.dev` только по https: вся доменная зона — в списке HSTS preload. Переход нужен программам — скриптам, серверам, curl. Заголовок HSTS не ставим: для `.dev` он уже действует, а включённый вручную его трудно отменить.
- `pnpm cdn check` проверяет переход у обоих хостов: последний адрес — манифест по `http://`, ждём 301 или 308 с `Location` на тот же адрес по https; колонка «HTTPS». Подсказка — Always Use HTTPS у Cloudflare или Force SSL у Bunny.

Уточнение от 23 октября 2026 (шаг 7 фазы 2, edge API, ADR-0024):

- Ответы API — `public, max-age=604800`, как в таблице. Ошибки запроса (4xx) — `public, max-age=300`, сбои (5xx) — `no-store`.
- **Сброса кэша API после выпуска набора нет** (решение владельца): версия набора входит в ключ кэша.
  - Функция перечитывает манифест из R2 раз в минуту и после выпуска берёт новые ключи. Старые ответы в кэше CDN больше никто не читает, и они вытесняются сами.
  - В браузерах прежний ответ живёт до недели, как и было задумано.
  - Так не нужен ещё один ключ — с правом сброса кэша — и шаг в «Выкладке».
  - Ключи кэша — свои (Cache API), сбросить их по адресу нельзя. Чтобы сбросить всё без правки кода, поднимается `CACHE_GENERATION` в `apps/api/src/config.ts`: это даёт новую метку сборки и новые ключи.
- **Кэш манифеста на CDN** (пункт бэклога, отложенный до этого шага): манифест остаётся мимо кэша CDN. Сброс через API не понадобился, а прежние доводы в силе: проверка и мониторинг видят файл в хранилище, запросов к нему мало.
- **Заголовки API ставит сама функция**: правила Cloudflare для `cdn.iconavo.dev` её не касаются.
  - CORS, `nosniff`, CORP, у SVG — та же CSP.
  - `Access-Control-Expose-Headers` открывает чужим сайтам `X-Cache`, `X-Iconavo-Build` и `X-Iconavo-Version`.
  - Сжатие `br` и `gzip` делает Cloudflare; проверяет его `pnpm api check`.
  - `OPTIONS` функция поддерживает: 204 с CORS, как у Iconify.

Почему: долгий кэш — главный источник скорости, а правила безопасности защищают пользователей, даже если санитайзер что-то пропустит.
