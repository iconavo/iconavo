# ADR-0035. Тесты и проверки

Статус: принято 16 октября 2026 по рекомендации.

Вопрос: как убедиться, что пакет работает у пользователей так же, как в песочнице?

Решение:

- Модульные тесты на Vitest для ядра: очередь, повторы, отсутствующие иконки, запасные хосты. Покрытие ядра тестами — не ниже 90%.
- Браузерные тесты на Playwright в Chromium, Firefox и WebKit.
- Визуальное сравнение иконок из пакета с SVG из фазы 1 через pixelmatch: расхождений быть не должно.
- Сбои сети: тесты блокируют основной хост и edge API, замедляют сеть и проверяют, что иконки всё равно появляются.
- Доступность: автоматическая проверка axe-core для иконок с подписью и без.
- Серверный рендер: пример на Next.js собирается и открывается без предупреждений о гидратации.
- Всё это запускается в CI на каждый pull request.

Почему: вы не читаете код, поэтому тесты — ваша гарантия, что изменение ничего не сломало.

Уточнение от 27 октября 2026 (шаг 5 фазы 3; решение владельца — Playwright сейчас, а не в шаге 9):

- **Playwright 1.64.1** — точная версия, в зависимостях конвейера. Браузеры ставятся один раз: `pnpm exec playwright install webkit firefox` (около 190 МБ, в `%LOCALAPPDATA%\ms-playwright`). Chrome — установленный, через `channel: "chrome"`.
- **WebKit вместо Safari.** Safari на Windows нет, и на шаге 5 его заменяет WebKit Playwright — движок Safari. По документации Playwright у WebKit на Windows отличаются видео, графика и сеть; ближе всего к Safari — WebKit на Mac.
- **`pnpm sandbox --check`** — проверка тега без интернета. Песочница и превью API поднимаются на свободных портах, браузеры идут по очереди. Что проверяется:
  - регистрация двух копий;
  - стили и Trusted Types при строгой CSP;
  - ошибки и нарушения политики;
  - предупреждения;
  - задержка и вид заглушек, в том числе без анимации;
  - рамка, перекраска, подпись, место до загрузки и ленивая загрузка.

  Отчёт — `.cache/reports/sandbox/check.html`, таблица и снимки каждого браузера.
- **Подпись** проверяется только в Chrome — по дереву доступности браузера. В Firefox её проверяют Экранным диктором вручную, в WebKit на Windows скринридера нет.
- **Плавность прокрутки** проверяет владелец глазами: `pnpm sandbox --browser=webkit|firefox|chrome` открывает песочницу в окне браузера.
- **В CI** браузерной проверки пока нет — это шаг 9. Тесты тега в Vitest идут в Node на маленькой подделке DOM, без новых зависимостей.

Уточнение от 28 октября 2026 (шаг 7 фазы 3, React и Next.js):

- **Тесты React в Vitest** — серверная разметка через `react-dom/server` в Node: обёртка, заглушки, ID, подпись, неверные значения, правило «ядро сервера не читается». Эффекты и гидратацию проверяет браузер: библиотеки DOM для Node (happy-dom) не добавляли.
- **`pnpm example --check`** — пример `examples/next` в режиме разработки (`next dev`) и в продакшен-сборке (`next build`, `next start`), в Chrome, Firefox и WebKit по очереди.
  - Сеть не нужна: хосты иконок — превью API на свободном порту.
  - Что проверяется:
    - серверный HTML (контекст без JavaScript);
    - «без мигания»: сторож DOM и одинаковые снимки раздела до и после гидратации;
    - консоль и строгая CSP продакшена;
    - заглушки: сразу после гидратации скрыты, через 0,25 с видны — скелетон мерцает, спиннер крутится. Снимок этого момента — в отчёте: на снимке «сразу после загрузки» заглушек ещё не видно, и он сбивал с толку (замечание владельца 28 октября 2026);
    - запросы к хостам;
    - клиентский компонент и переход по ссылке;
    - подпись (Chrome), Trusted Types, рамка, тег в React.
  - Сведения для ADR: какой вход тега выбрал Next.js и работает ли `var()` в атрибуте `color`.
  - **Контрольный запуск** портит заголовок страницы сразу после разбора HTML и ждёт сообщения о гидратации. Другое сообщение не в счёт: проверка не должна быть слепой.
  - **Почему оба режима.** Расхождение текста React 19 сообщает и в продакшене (ошибка #418), а расхождение атрибутов — только в сборке для разработки. Поэтому без `next dev` проверка не увидела бы, например, лишний класс у `<svg>`.
  - Отчёт — `.cache/reports/example/check.html` со снимками, код 1 — есть проблемы. `--webpack` — то же со сборщиком webpack.
  - Снимки — через помощника песочницы: стиль, который Playwright вставляет для снимка, строгая CSP WebKit отклоняет, и эти нарушения не в счёт.
- **React 18** в браузере проверит шаг 9: App Router рисует своей сборкой React 19, а React 18 под другим именем не ставили (решение владельца).

Уточнение от 28 октября 2026 (шаг 9 фазы 3; решения владельца — все три новые зависимости, браузерные проверки обязательны для слияния, визуальное сравнение всего каталога в трёх браузерах на каждом PR, эталон — SVG из `data/`):

- **Отчёт простыми словами** — [docs/tests.md](../tests.md): каждое обещание README и чем оно проверено, и что не проверено.
- **CI.** Задача `browser` в `ci.yml` — Chrome, Firefox и WebKit параллельно, по задаче на браузер:
  - подряд идут `pnpm sandbox --check`, `pnpm example --check` и `pnpm visual`, каждая — даже если предыдущая упала;
  - таблицы — в сводке запуска, HTML-отчёты — артефакты на 14 дней (`sandbox-…`, `example-…`, `visual-….html`);
  - Chrome — установленный в образе ubuntu-latest, Firefox и WebKit — `playwright install --with-deps`, сборки — в кэше по версии Playwright.

  Итог трёх задач — `browsers`, обязательная проверка `main` вместе с `check` и `data`. Новый пуш в PR отменяет прошлый запуск.
- **Покрытие** — `@vitest/coverage-v8` 5.0.5, `vitest.config.ts`. Порог 90% строк, веток и функций — только у ядра, `pnpm test --coverage` в CI и в `pnpm check`. 28 октября 2026:
  - ядро — 100% строк, 95% веток, 100% функций;
  - тег — 99%, 97%, 100%;
  - React — 93%, 87%, 81%: эффекты и гидратацию модульные тесты в Node не запускают, их проверяет браузер.
- **Linux.** Остановка Next.js ждёт выхода процесса (SIGTERM группе, через 10 с — SIGKILL): иначе `next build` в той же папке застал бы `next dev`. Записи Firefox «CORS request did not succeed» о запросе без ответа — не ошибки страницы, как «Failed to load resource» у Chrome; настоящую ошибку CORS Firefox называет иначе.
- **Заглушки меряются по их собственной анимации задержки** (Web Animations API): скрыта в первом кадре после старта анимации, видна после её конца. Таймером от смены класса мерить нельзя: WebKit на Linux в CI запускает CSS-анимацию на следующей отрисовке кадра, и через 50 мс заглушка «ещё видна», а через 250 мс после гидратации «ещё скрыта».
- **Сбои сети в браузере** — страница песочницы `/net` и пять строк `pnpm sandbox --check`:
  - API отказал;
  - API и первый хост статики отказали;
  - API молчит;
  - медленная сеть (+2 с);
  - ничего не отвечает.

  Отказы и задержки задаёт Playwright (`page.route`) — сеть браузера, а не подмена `fetch`. Каждый сценарий — в чистом контексте. Второй хост статики — второе превью API на другом порту. Ядро о проверке не знает.
- **Визуальное сравнение** — `pnpm visual`, код `packages/pipeline/src/visual/`:
  - **что сравнивается:** каждое имя пяти наборов — 44 398 иконок и алиасов, — через тег (скрипт для страниц без сборщика, `addIcons`, `noobserver`) и через React (серверный HTML `IconavoProvider` и `Icon`);
  - **эталон** — `svgOf(effectiveIcon())`, те же байты, что у файла `cdn.iconavo.dev`, в `<img>`;
  - **размер и страницы** — 2 px на единицу сетки, страницы по 500 имён: три сетки одним снимком, шаг между сетками кратен 512 px;
  - **сравнение** — pixelmatch с порогом контроля качества (0,1, сглаживание не в счёт);
  - **допуск** — 0,5% пикселей иконки (12 при 48 px). SVG-картинку и SVG в странице браузер сглаживает по-разному: у иконок с мелкими деталями (буквы в `csv`, `fiber-new`) Chrome расходится на 1–6 пикселей края. От места иконки внутри плиток отрисовки это тоже зависит, поэтому сетки стоят с одинаковым смещением. Иконки в допуске — отдельным разделом отчёта, с картинками;
  - **не слепое:** контрольная клетка на каждой странице обязана разойтись больше допуска; пустой эталон — проблема;
  - **итог 28 октября 2026:** расхождений больше допуска нет ни в одном браузере. Весь каталог: Firefox — 57 с, WebKit — 98 с, Chrome — около 8 минут на компьютере владельца. PNG снимков читает свой декодер (`qc/png.ts`), без зависимостей.
- **React 18** — `examples/next` без Next.js (`example/react18.ts`):
  - rolldown собирает `app/page.tsx` и `app/client.tsx` для сервера (`renderToString`) и браузера (`hydrateRoot`), заменяя `react` и `react-dom` на 18.3.1 — пакеты `react-18` и `react-dom-18` конвейера; обёртка и `/more` — свои, синхронные;
  - политика строже, чем у примера: скрипты только своими файлами и обязательные Trusted Types;
  - разметка та же, поэтому проверяют те же функции — столбцы «React 18», разработка и продакшен;
  - 28 октября 2026 в Chrome — все строки «да»: контрольный запуск поймал «Text content did not match» в разработке и ошибку #425 в продакшене.
- **Доступность** — axe-core 4.14.0, строка `axe` в `pnpm example --check`:
  - главная и `/more` после гидратации, правила WCAG 2.2 A и AA, в контексте без CSP — иначе скрипт axe не пустят;
  - подпись тега через ElementInternals axe не видит (Deque: они невидимы, пока компонент сам их не откроет, axe-core 4.13+), поэтому её по-прежнему проверяет дерево доступности Chrome.
- **«Ничего не хранит в браузере»** (README) — тест сборки: в скрипте тега и в сборке React нет cookie, `localStorage` и других хранилищ.
- **Без интернета.** Запросы страниц примера к живым хостам иконок проверка обрывает и показывает в строке «Сеть». У Next.js `/more` для axe открывается переходом по ссылке, как у пользователя: хосты задаёт клиентский компонент главной, а прямой заход брал хосты по умолчанию. WebKit с `bypassCSP` политику не снимает (ни Trusted Types, ни `connect-src`), поэтому страницы React 18 для axe отдаются без политики по `?axe=1`.
- **Тесты не слепые** — черновой PR #85 с нарочно сломанным `replaceIds` (ссылки на ID не переписываются).
  - Модульные тесты падают.
  - Визуальное сравнение ловит `fluent-emoji-flat:eleven-oclock`: пропадает красная стрелка с заливкой градиентом по ссылке на ID — 39–40 пикселей при допуске 21.
  - Остальные 20 иконок с ID сломанные ссылки рисуют почти так же: обрезка на весь холст, едва видимый фильтр, тонкие градиенты скрипки (6 пикселей). Поэтому целость ссылок по всем иконкам проверяют модульные тесты (`svg-core.test.ts`), а не только картинка.
- **Время задачи `browser` в CI**, 28 октября 2026, вместе с установкой: Firefox — 3 мин, Chrome — 7,5 мин (из них визуальное сравнение — около 6), WebKit — 8 мин.
- **Приёмка** — владелец 29 октября 2026 (PR #84).
