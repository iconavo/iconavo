# ADR-0030. Загрузка иконок в ядре

Статус: принято 16 октября 2026 по рекомендации, с опорой на Iconify.

Вопрос: как ядро получает иконки быстро, экономно и без сбоев?

Решение:

- Хранилище в памяти: набор → иконки, у каждой состояние — загружена, загружается, нет, ошибка.
- Запросы копятся до конца текущего тика и уходят пачкой: один запрос на набор, имена отсортированы, адрес не длиннее 500 символов. Так же работает Iconify ([источник](https://iconify.design/docs/api/icon-data.html)).
- Повторный запрос той же иконки в сеть не уходит: второй компонент ждёт ответа на первый.
- Имена из `not_found` запоминаются и больше не запрашиваются, а сетевые ошибки повторяются через 1, 2 и 4 секунды.
- Порядок хостов: пачка через `api.домен`, затем поштучно со статики `cdn.домен`, затем со статики `cdn2.домен`. Для статики ядро сначала читает манифест, чтобы узнать версию набора.
- Если хост молчит 750 мс, тот же запрос уходит на следующий; общий таймаут — 5 секунд, как у Iconify ([источник](https://iconify.design/docs/api/providers.html)).
- Постоянного кэша в браузере нет, только память и HTTP-кэш. Iconify отказался от localStorage в 2025 году ради соответствия GDPR ([источник](https://iconify.design/news/2025.html)).
- Расширения: `addIcons` для работы без сети, `setLoader` для своих источников, `configure` для своих хостов.

Уточнение от 26 октября 2026 (шаг 1 фазы 3, README пакета; решения владельца — свой хост и запасные адреса):

- **Хосты по порядку:** `api.iconavo.dev` пачками → `cdn.iconavo.dev` → `cdn2.iconavo.dev` → `iconavo.b-cdn.net` по одной иконке, с манифестом своего хоста. Собственный адрес зоны Bunny не зависит от DNS Cloudflare (ADR-0025) — решение владельца.
  - jsDelivr для иконок не берём: в пакетах npm лежат только целые наборы, от 0,1 до 1,5 МБ в сжатом виде.
  - Список по умолчанию попадает в CSP сайтов (`connect-src`): добавить в него адрес позже — сломать сайты со строгой CSP. Поэтому список зафиксирован сейчас.
- **`configure({ api, cdn, placeholder, dev })`.**
  - `api` — адреса API, отвечающих на пачки как Iconify API; `cdn` — хосты статики с раскладкой ADR-0022.
  - Каждый список заменяет наш целиком, наши адреса — только если дописать их явно (решение владельца: свой сервер ставят ради приватности и правил безопасности). `[]` выключает уровень.
  - Неуказанные настройки сохраняются; изменение действует на следующие запросы, поэтому `configure` вызывают до первой иконки.
  - `placeholder` и `dev` — в ADR-0031.
- **Что должен отдавать свой хост.**
  - Для `api` — `GET /{набор}.json?icons=a,b`: IconifyJSON с цепочками алиасов и `not_found`; неизвестный набор — 404. Ответ 200 с телом `404` — так Iconify API отвечает на неизвестный набор (ADR-0024) — ядро понимает так же, поэтому для пачек подходит и свой сервер Iconify API.
  - Для `cdn` — `manifest.json` и `v/{версия}/{набор}/{имя}.json`.
  - Оба — с CORS. Ядро шлёт только простой GET без своих заголовков: предварительный `OPTIONS` у R2 получает 403 (ADR-0023).
- **`addIcons(data | data[])`** — IconifyJSON одного набора или массив таких.
  - Подходит ответ пачки API, `icons` пакета данных, пакеты Iconify `@iconify-json/*` и свои иконки со своим префиксом по правилу ADR-0001; имена с `@` заняты под будущие приватные наборы.
  - Добавленные иконки в сеть не запрашиваются, заменяют одноимённые, а такие иконки на странице перерисовываются. `not_found` запоминается как «нет». Неверный префикс — исключение: это ошибка разработчика.
- **`setLoader(prefix, loader | null)`** — `loader(names) → Promise<IconifyJSON | null>` вместо хостов для одного набора, в том числе нашего.
  - Зовётся пачкой за тик, без повторов имён. Ответ добавляется как через `addIcons`; чего в нём нет, и ответ `null` — «нет иконки».
  - Отказ — как сбой хоста, с повторами. `null` вместо функции снимает загрузчик.
- **`loadIcons(names) → Promise<IconifyJSON[]>`** — по объекту на набор, с `not_found`; никогда не отклоняется.
  - Один полный проход по хостам, до 5 секунд, без повторов через 1, 2 и 4 секунды: серверный рендер не может ждать ~20 секунд.
  - Не загрузившихся имён в ответе нет — компоненты в браузере догрузят их сами. Неверное имя — в `not_found` с предупреждением.
- **После всех повторов** иконка выглядит как отсутствующая, но имя не запоминается: при следующем появлении её запросят снова.
- **Доверие.** Данные иконок, хосты и загрузчики становятся разметкой страницы, поэтому README просит доверять им как скриптам. Санитайзера в ядре нет: наши данные очищены конвейером (ADR-0013), а для чужих он не влез бы в бюджет размера (ADR-0034).

Уточнение от 27 октября 2026 (шаг 2 фазы 3, ядро и песочница; решение владельца — оставить 500 символов):

- **Пачки.** 500 символов — на весь адрес, с хостом. Сверх того — не больше 100 имён: больше edge API не принимает (ADR-0024). На наших наборах это 20–40 имён на запрос, и 100 иконок одного набора дают 3–5 запросов: у Lucide, Tabler и Material Symbols — 4, у Phosphor и Fluent Emoji — 5.
  - Решение владельца — оставить 500 символов, как у Iconify, а не поднимать до 2000 ради одного запроса. Пачку мимо кэша функция собирает из R2 по 6 файлов за раз: 100 имён — около 17 раундов, 30 — около 5. Несколько небольших пачек уходят параллельно и приходят раньше, реже упираясь в порог 750 мс шага 3.
  - Куски идут параллельно, имена по кодам символов — одинаковые страницы дают одинаковые адреса, и ответы берутся из кэша.
- **Тик** — `setTimeout(…, 0)`, как у Iconify: в пачку попадают запросы текущей задачи и всех её микрозадач (так рисуют фреймворки), следующая задача — новый запрос.
- **Состояния** — в общем хранилище, по полному имени `набор:иконка`:
  - «загружена» — данные, готовые к рисованию: цепочка алиасов разрешается сразу при получении, как у Iconify;
  - «загружается»;
  - «нет» — `not_found`, имени нет в ответе, неизвестный набор (404 или, как у Iconify API, ответ 200 с телом `404`), алиас не разрешился. До конца жизни страницы не запрашивается;
  - «ошибка» — сбой сети, другой код ответа, не JSON, чужой `prefix`, нет хоста. Запрашивается снова при следующем показе.
  - Ответ хоста и загрузчика заполняет только незагруженные имена; `addIcons` заменяет загруженные и перерисовывает их. «Нет» загруженную иконку не заменяет никогда.
  - Неверное имя — сразу «нет», без запроса. Для показа «нет» и «ошибка» одинаковы (ADR-0031).
- **Две копии ядра на странице.** В браузере общий объект лежит под `Symbol.for("iconavo.core.1")`: иконки, слушатели, настройки `configure` и загрузчики `setLoader`. Очередь у каждой копии своя. Общего состояния «загружается» хватает, чтобы копии не запросили одно имя дважды, а устройство очереди можно менять без новой версии формата. Поля объекта только добавляются; убрать или изменить поле — новая версия в ключе. На сервере у каждого модуля своё (ADR-0033).
- **Доступ для адаптеров** — `@iconavo-ui/core/internal` (ADR-0029):
  - `getIcon(name)` — состояние без побочных эффектов, тот же объект при повторе (для `useSyncExternalStore`). Имя, которое ещё не просили, — «загружается»: запрос после подписки не меняет картинку;
  - `subscribeIcon(name, listener)` — только подписка, возвращает отписку;
  - `loadIcon(name)` — запрос. Подписка сама ничего не запрашивает: иначе повторная подписка React после «ошибки» слала бы запросы по кругу.
- **Ответ хоста дочитывается всегда**, даже 404: так Node освобождает соединение (`loadIcons` на сервере).
- **Для шага 3:**
  - куски считать по самому длинному хосту списка, чтобы при переходе на следующий хост они остались в пределах 500 символов;
  - таймаут 5 с — с отменой запроса (`AbortSignal.timeout`), а не только без ожидания ответа;
  - повторы через 1, 2 и 4 с — пока иконка кому-то нужна: таймеры `loadIcons` на сервере держали бы процесс.
- **Песочница** — `pnpm sandbox`, `http://127.0.0.1:4282`: 100 иконок и журнал запросов для сверки с DevTools.

Уточнение от 27 октября 2026 (шаг 3 фазы 3, ошибки и запасные хосты; решение владельца — предупреждение при сбое загрузки, ADR-0031):

- **Попытка** устроена как `sendQuery` у Iconify и идёт на кусок имён.
  - Источники по очереди: пачка с каждого хоста `api`, затем статика с каждого хоста `cdn`. У набора с `setLoader` источник один — загрузчик. Список собирается на каждую попытку заново, по настройкам на этот момент.
  - Источник молчит 750 мс — следующий спрашивается параллельно. Отказал, а ждать больше некого, — следующий сразу.
  - Источник получает только открытые имена — те, что в хранилище ещё «загружается». Ответ другого хоста, `addIcons` и другая копия ядра сами сокращают список.
  - Ответ есть у всех имён — остальные запросы отменяются. Через 5 с от начала попытки отменяется всё, а открытые имена идут в повтор.
- **Статика:**
  - манифест — один запрос на хост за жизнь страницы, общий для всех попыток копии ядра. У него свой контроллер и таймер 5 с: законченная попытка не отменит его остальным. Не прочитался — забывается и запрашивается снова в следующей попытке;
  - если попытка закончилась, пока ждали манифест, файлы не запрашиваются;
  - версия из манифеста становится частью адреса, поэтому проверяется правилом имён ADR-0001;
  - файл на имя, каждый пишет свой ответ сразу. Не пришедший файл оставляет открытым только своё имя, и оно идёт к следующему хосту.
- **Исходы:**

  | Что пришло | Состояние | Повтор |
  | --- | --- | --- |
  | Иконка в ответе | данные | — |
  | `not_found`, имени нет в ответе, 404 или тело `404` у API, 404 файла статики, набора нет в манифесте хоста, загрузчик вернул `null` | «нет» и предупреждение | никогда; другие хосты не спрашиваются |
  | Ошибка сети, CORS или CSP, таймаут, 5xx, другие 4xx, не JSON, чужой набор, битый манифест; отказ или молчание загрузчика дольше 5 с | сбой: следующий источник, после последнего — повтор | через 1, 2 и 4 с |
  | Четвёртая попытка не удалась или иконку больше никто не показывает | «ошибка» и предупреждение с причиной | при следующем показе |
  | Хостов нет совсем (`configure({ api: [], cdn: [] })`) | «ошибка» сразу | нет |

- **Повторы** — только пока иконка нужна: у имени есть слушатель, кроме ожидания `loadIcons`. Проверка — после попытки и ещё раз в конце паузы. На сервере таких слушателей нет, поэтому нет и таймеров повторов.
- **`loadIcons`** — один проход. Его слушатели помечены, и имя, которое ждёт только он, после неудачной попытки сразу становится «ошибкой». Имя, которое повторяют ради иконки на странице, он ждёт не дольше 5 с. В ответ не попадают ни «ошибка», ни то, что ещё грузится. После ответа таймеров не остаётся.
- **Отмена** — `AbortController` с `setTimeout`, а не `AbortSignal.timeout`, как предполагало уточнение шага 2. Тот же контроллер отменяет проигравших, когда ответ есть у всех имён. А таймеры `setTimeout` подчиняются поддельному времени тестов: `AbortSignal.timeout` его не видит.
- **Хост, который подвёл, не запоминается:** каждая новая пачка начинает с `api`. Если API молчит, иконки появляются на 0,75 с позже. Зато короткий сбой не переводит страницу навсегда на статику, где запросов в 25 раз больше. У Iconify последний ответивший хост становится первым; у нас это кандидат после беты (бэклог).
- **Медленная сеть:** пачка API приходит около порога 750 мс, поэтому уходят и запросы к статике, которые потом отменяются. Песочница это показывает; замер — на учениях фазы 5 (бэклог).
- **Песочница** — «Условия сети» по варианту владельца: сценарии и каждый хост.
  - Сценарии «Всё работает», «Основной хост недоступен», «Медленная сеть», «Ничего не отвечает».
  - У каждого хоста — «работает / недоступен / молчит / медленный (+2 с)».
  - Флажок «Добавить иконки, которых нет».
  - Сбои изображает обёртка `fetch` страницы, ядро о них не знает. Что обёртка не пропустила, в сеть не уходит, поэтому «ушло в сеть» в журнале совпадает с DevTools.
  - В режиме превью всё на этом компьютере: API и статика `/_static/` превью.

Почему: сто иконок на странице — это 3–5 запросов вместо ста, а сбой одного хоста пользователь не замечает.
