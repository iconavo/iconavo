# ADR-0033. React и серверный рендер

Статус: принято 16 октября 2026 по рекомендации.

Вопрос: как компонент React работает в Next.js с серверным рендером без мигания и ошибок?

Решение:

- Компонент поддерживает React 18 и 19 и работает в Next.js App Router.
- Если иконка уже есть в ядре — загружена заранее через `loadIcons` или добавлена через `addIcons`, — она сразу попадает в серверный HTML.
- Иначе сервер и браузер рисуют одинаковую заглушку нужного размера, а иконка подгружается после гидратации. Разметка совпадает, поэтому ошибок гидратации нет.
- Для страниц, где иконки известны заранее, есть рецепт в документации: загрузить их на сервере и передать в браузер — тогда мигания нет совсем.
- Пример на Next.js входит в тесты (ADR-0035).

Уточнение от 26 октября 2026 (шаг 1 фазы 3, README пакета; решение владельца — имя обёртки):

- **Поправка.** Пункт «если иконка уже есть в ядре… она сразу попадает в серверный HTML» для Next.js App Router неверен.
  - Модуль, нужный и серверным, и клиентским компонентам, Next собирает отдельно для каждой среды ([документация Next.js](https://nextjs.org/docs/app/guides/server-and-client-boundary)). Поэтому `loadIcons` в серверном компоненте не наполняет ядро клиентских.
  - Память сервера общая для всех запросов: иконка, попавшая в ядро на чужом запросе, нарисовалась бы на сервере, но не в браузере, — ошибка гидратации.
- **Правило.** На сервере и при гидратации `Icon` рисует только данные из обёртки `IconavoProvider icons={…}` (решение владельца об имени), после гидратации — из общего ядра. Остальные иконки и на сервере, и при гидратации — одинаковая заглушка нужного размера.
- **Рецепт без мигания:** серверный компонент вызывает `await loadIcons([...])` и передаёт результат в `<IconavoProvider icons={icons}>`.
- `addIcons` на уровне модуля работает, но иконка появляется сразу после гидратации. Вызывать `addIcons` во время рендера нельзя — данные утекли бы в чужие запросы. `setLoader` принимает функцию, а её нельзя передать с сервера, поэтому его вызывают в клиентском модуле.
- `"use client"` — только у модулей компонентов. У входа пакета его нет, иначе `loadIcons` в серверном компоненте не вызвать; сборка пакета должна эти пометки сохранить.
- Компонент всегда рисует `<svg>`, и во время загрузки тоже; остальные пропсы (`className`, `style`, обработчики, `ref`) уходят на него. ID масок — через `useId`: счётчик ломает гидратацию. В серверном HTML нет атрибутов `style` (строгая CSP).
- Проверка — в шаге 7, вместе с примером на Next.js. Если механика не сойдётся, README поправляется там же.

Уточнение от 28 октября 2026 (шаг 7 фазы 3; решения владельца — зависимости, стили из скрипта, бюджет 2,5 КБ):

- **Главное правило.** На сервере и при гидратации разметка `Icon` зависит только от пропсов, данных обёртки и чистых функций ядра. Хранилище, настройки `configure`, режим разработки и `CSS.supports` в этот путь не входят: на сервере и в браузере они могут различаться. Всё, что от них зависит, живёт в листе стилей и в эффектах браузера.
- **Состояние** читается из ядра через `useSyncExternalStore` (`packages/react/src/state.ts`):

  | Когда | Что рисует `Icon` |
  | --- | --- |
  | Сервер и гидратация (`getServerSnapshot`) | Иконку из обёртки; имя из её `not_found` и неверное имя — «нет»; остальное — заглушку |
  | После гидратации и отрисовка только в браузере (`getSnapshot`) | Иконку ядра; иначе из обёртки; иначе «нет» обёртки; иначе состояние ядра |

  - Иконки обёртки после гидратации тот же объект, поэтому React их не перерисовывает и в сеть они не идут.
  - `addIcons` в модуле даёт иконку сразу после гидратации; замена через `addIcons` перерисовывает и иконки обёртки.
- **Запрос** — `loadIcon` в эффекте при монтировании и смене имени, если иконки нет в обёртке.
  - Эффект — после подписки: повторы ядра идут, пока у имени есть слушатель (ADR-0030).
  - «Ошибка» запрашивается снова при следующем монтировании.
  - Двойные эффекты StrictMode безопасны.
- **`not_found` обёртки.** Имя при гидратации рисуется как «нет», а браузер переспрашивает его сам, без заглушки: появится, если иконка у хоста есть. Так закрыт пункт бэклога «„Нет“ на сервере живёт до перезапуска» — устаревшее «нет» сервера чинит браузер.
- **Обёртка** ищет иконку лениво (`iconData` ядра, с алиасами) и кэширует по имени: `useSyncExternalStore` нужен тот же объект при повторе. Вложенная обёртка ищет сначала у себя; её `not_found` не заслоняет иконку внешней.
  - В ядро обёртка ничего не пишет: на сервере его память общая для всех запросов, а запись во время отрисовки разбудила бы чужие иконки посреди неё.
  - Поэтому тег `<iconavo-icon>` иконок обёртки не видит и грузит свои сам — README обещает обёртку только компонентам внутри неё.
- **Next.js.** Серверные и клиентские компоненты Next.js собирает отдельно, и у каждой сборки своя копия хранилища. `configure`, `setLoader` и `addIcons` в модуле — в файле, который импортируют и layout, и клиентский компонент; README поправлен.
- **Подпись** — и у заглушки: у кнопки из одной иконки есть имя, пока иконка грузится.
- **Пакет** (`packages/react`): вход без `"use client"`, у `icon.ts` и `provider.ts` — первой строкой, это проверяет тест на `dist/`; `"sideEffects": false`; без JSX — `createElement`; `forwardRef` для React 18. Сборка `import { loadIcons } from "@iconavo-ui/react"` выбрасывает компоненты и сам React — тест конвейера.
- **Стили** заглушек, рамки и `inline` — лист `document.adoptedStyleSheets` из `useInsertionEffect` (решение владельца, ADR-0031). До загрузки скриптов в серверном HTML — пустое место нужного размера, `inline` опускает иконку после загрузки. Файл стилей для серверного HTML — в бэклоге, вместе с сайтом.
- **Trusted Types** — политика `iconavo` тега (ADR-0032). Рисунок уходит в `innerHTML` объектом TrustedHTML, один объект на строку рисунка: React сравнивает `__html` по ссылке и иначе переписывал бы рисунок на каждой перерисовке.
  - Политику не разрешили, а Trusted Types требуются (видно по одной пробной записи) — пустое место и одно предупреждение, как у тега. Иконки с сервера React тогда перерисует в браузере (восстановимая ошибка гидратации).
- **Проверка** — `pnpm example --check` (ADR-0035), 28 октября 2026: Next.js 16.4.3 и Turbopack, режим разработки и продакшен-сборка, Chrome, Firefox и WebKit.
  - Иконки обёртки — в серверном HTML, после загрузки ни одного изменения в DOM, снимок раздела до и после гидратации совпадает.
  - Иконки из браузера догружаются пачками, к иконкам обёртки — ни одного запроса.
  - В консоли — ни одного предупреждения о гидратации. Контрольный запуск портит HTML, и React это замечает: «Hydration failed…» в разработке, ошибка #418 в продакшене.
  - Строгая CSP продакшена (`style-src 'self'`) — ни одного нарушения.
  - Совместимость с React 18 проверит шаг 9: App Router рисует своей сборкой React 19.
- **Холодный сервер.** `loadIcons` в layout ждёт ответа хостов до 5 с, и пока хосты молчат, первый байт страницы задерживается; при `cacheComponents` Next.js его оборачивают в `"use cache"`. Бэклог.

Почему: Next.js — самый частый способ использовать React, и пакет должен работать там без дополнительной настройки.
