# ADR-0051. Выпуск пакетов для разработчиков

Статус: принято 29 октября 2026 (шаг 11 фазы 3). Продуктовые решения — владельца: каждый выпуск — PR с версией, журнал изменений — один английский файл и страница на сайте, в корне репозитория — английский README. Технические части приняты по рекомендации.

Вопрос: как ядро, тег и React выходят в npm — с какой версией, журналом и проверками, и кто решает, что версия готова?

## Версии и журнал

- **Одна версия у трёх пакетов** — `@iconavo-ui/core`, `@iconavo-ui/icon`, `@iconavo-ui/react` (ADR-0029). Тег и React зависят от ядра ровно этой версии: `workspace:*` в репозитории, а `pnpm pack` пишет в архив точный номер.
- **До запуска — 0.x под тегом `next`** (ADR-0005, ADR-0026, ADR-0036); 1.0 выходит в день запуска. В 0.x ломающее изменение API — `0.(y+1).0`, остальное — `0.y.(z+1)`. Номер не повторяется никогда, даже у снятой версии: npm не даёт занять его снова.
- **Выпуск — PR с версией** (решение владельца 29 октября 2026). Его делает `pnpm release bump X.Y.Z`, слияние PR — одобрение выпуска, публикует CI. Изменения сначала попадают в `main` и проходят проверки, и только потом — в npm. Ручной запуск «Выпуска пакетов» — для первой публикации нового пакета и чтобы продолжить выпуск, который остановился.
- **Журнал изменений** — `packages/icon/CHANGELOG.md`, по-английски, один на три пакета; на сайте — `/docs/changelog` (решение владельца 29 октября 2026).
  - Раздел — `## X.Y.Z — ГГГГ-ММ-ДД`, сверху — свежий. Текст раздела пишет Claude при выпуске по истории коммитов, владелец утверждает его в PR.
  - В архивы журнал не входит, как и у пакетов данных (ADR-0026): ссылка на страницу сайта — в пометке «Beta» README всех трёх пакетов.
  - Встроенные выпуски pnpm 12 (`pnpm change`, `pnpm version -r`) не подошли: журнал у них — в каждом пакете отдельно или только внутри архива, а адрес и хэш скрипта в README всё равно меняет наш код.
  - Сайт и README показывают `main`: правка API в README видна сразу, а в npm — со следующим выпуском. В бете это допустимо; выпуск после такой правки — не откладывать.

## Хэш скрипта и поля пакетов

- **Строка подключения скрипта тега** (ADR-0032) — с точной версией и хэшем `integrity` (SHA-384): в `packages/icon/README.md` (Install и пример HTML), в HTML-примере для StackBlitz и в корневом `README.md`. Хэш вписывает `pnpm release bump`.
  - `crossorigin` не ставим: модульный скрипт браузер и так загружает без cookies, режим `anonymous` для него уже по умолчанию.
  - jsDelivr отдаёт файл точной версии байт в байт и не меняет его: сжимает только по запросу `.min.js`.
  - Рецепт `configure` без сборщика импортирует скрипт из модуля, а `import` хэша не несёт. Защитить его можно через `integrity` в import map (Chrome 127, Firefox 138, Safari 18) — бэклог.
- **Поля `package.json`** — у трёх пакетов одинаковые, кроме папки; их сверяет подготовка.
  - `description`, `keywords`, `license: MIT`, `homepage: https://iconavo.dev/docs`, `bugs`.
  - `repository` — `git+https://github.com/iconavo/iconavo.git` с `directory: packages/{пакет}`: этот адрес npm сверяет с подписью provenance.
  - `publishConfig` — `{ access: public, provenance: true, tag: next }`: публикация с ноутбука без CI не пройдёт — provenance там не подписать.
  - `files: ["dist"]`, в `exports` — ещё `./package.json`. README и LICENSE `pnpm pack` кладёт сам: LICENSE — из корня репозитория.
  - Ни одного скрипта, который npm запускает сам (`postinstall`, `prepare` и другие).
- **Подсказки редактора у публичного API — по-английски.** Их разработчик видит при наведении на `configure`, `Icon` и их пропсы; тест `src/release/public-api.test.ts` не пускает туда кириллицу. Внутренние модули по-прежнему пишутся по-русски.
- **README ядра** — коротко, ставить не его, а тег или React; `@iconavo-ui/core/internal` может меняться в любой версии (ADR-0036).

## Команда `pnpm release`

Код — `packages/pipeline/src/release/`. Код пакетов данных (`src/npm/`) только импортируется — без правок: правка в нём запускает «Публикацию в npm».

- **`pnpm release bump [версия]`** — правит репозиторий; реестр npm только читается: вышла ли нынешняя версия.
  - Версия — вида X.Y.Z без ведущих нулей, выше нынешней, до запуска — 0.x.
  - Сначала собирает скрипт тега и читает все файлы, потом пишет: сбой не оставляет выпуск наполовину.
  - Ставит версию трём пакетам и примерам React и Next.js, снимает `private`.
  - Журнал: раздел этой версии уже первый — меняет только дату. Первый раздел — нынешняя версия, которая так и не вышла (выпуск передумали на другую), — он переходит к новой версии вместе с текстом. Иначе — новый раздел с заготовкой `TODO`.
  - Пишет адрес с версией и хэш свежей сборки в строки подключения.
  - Удаляет lock-файлы примеров с другой версией наших пакетов: новые пишет `pnpm starters --lock` после публикации.
  - Без версии — только хэш и дата, пока версия не вышла: после правок кода до слияния. Версия уже в npm — ошибка: хэш вышедшего скрипта не меняется, для правок нужна новая версия.
- **`pnpm release prepare [--first]`** — то, что делает CI в «Подготовке»: архивы `pnpm pack` и план в `dist-release/` (в git не идёт). Реестр npm только читается. Отчёт — `.cache/reports/release/prepare.html`, таблица — в сводке запуска. Та же подготовка — шаг обязательной задачи `check` на каждом PR: выпуск с устаревшим хэшем или без раздела журнала не сольётся.
  - Проверки:
    - одна версия у трёх пакетов, поля `package.json` — дословно;
    - раздел журнала этой версии — первый; заготовки `TODO` нет нигде; даты и порядок верные; разделы ниже первого — только версии, которые есть в npm;
    - строки подключения — одной версии и с одним хэшем верного вида;
    - архивы: только `package.json`, README, LICENSE и `dist/`; каждый путь из `exports`, `types` и `sideEffects` есть в архиве; у каждого файла `dist` есть исходник в `src` — так ловится забытая старая сборка; LICENSE и README — те же, что в репозитории;
    - хэш README: версии нет в npm — он равен свежей сборке, иначе — скрипту опубликованного архива.
  - Реестр:
    - пакета нет — «ждёт первой публикации»; без `--first` не публикуется ни один пакет: тег и React не выйдут без ядра;
    - номер не выше когда-либо вышедшего или уже снятый — «СТОП»;
    - у пакета только заготовка npm `0.0.0-stage` — «СТОП»: npm ещё обрабатывает первую публикацию;
    - вышла часть пакетов (сбой посередине) — вышедшие обязаны совпасть со свежей сборкой файл в файл, тогда выйдут остальные; иначе «СТОП: поднимите версию всем трём»;
    - все три уже в npm — публиковать нечего.
  - План пишется, только если «СТОП» нет: версия, тег, коммит запуска, хэш скрипта и по пакету — действие, версия под `next` до публикации, публиковать ли, архив и его SHA-512. Порядок — ядро, тег, React.
- **`pnpm release verify --plan=… [--wait=N]`** — после публикации. Ждёт до N секунд: npm показывает новую версию и её подпись через минуты.
  - Под `next` — версия плана; архив в npm — ровно архив «Подготовки» (SHA-512).
  - Подпись provenance — `https://github.com/iconavo/iconavo`, `.github/workflows/release.yml`, `refs/heads/main`, коммит плана; подписан именно этот архив.
  - Выложено доверенной публикацией; токен допустим только у первой версии пакета.
  - jsDelivr отдаёт скрипт с хэшем README и `Access-Control-Allow-Origin: *`.
  - jsDelivr отвечает 404, 429 или 5xx — проверка ждёт: он забирает новую версию из npm не сразу.
  - **Чистый проект** — пустая папка `.cache/release/clean`, `npm install` тега, React и `react`/`react-dom` 19.3.1 из реестра — до 4 попыток через 30 секунд: сокращённое описание пакета, по которому npm ищет версию, реестр обновляет позже полного. Затем:
    - по одной копии каждого нашего пакета;
    - `npm audit signatures`;
    - Node загружает `lucide:house` с живых хостов через `loadIcons` и рисует `IconavoProvider` и `Icon` через `renderToString`;
    - рисунок совпадает с `data/`, иконка — в отчёте `.cache/reports/release/verify.html`.

## Workflow «Выпуск пакетов»

`.github/workflows/release.yml` — по образцу «Публикации в npm» (ADR-0026).

- **Запуски:**
  - push в `main` при изменении трёх `package.json` — это слияние PR выпуска; README тега, журнала, HTML-примера, корневого README или самого workflow — так выпуск, остановленный «СТОП» (например, устаревшим хэшем), продолжает PR с исправлением. Вышедшую версию подготовка второй раз не выпустит;
  - на PR с правкой кода выпуска или workflow — только показ: секретов там нет. Подготовку на каждом PR делает задача `check`;
  - вручную — «Первая публикация» и «Только показ»; ручной запуск без флажков продолжает остановившийся выпуск.

  Выпуски из `main` идут по одному (группа `release`) и не прерываются. Показы, в том числе «Только показ» на `main`, — каждый в своей группе: в общей GitHub отменил бы ждущий выпуск.
- **«Подготовка»** — права только на чтение: install, `pnpm release prepare` (с `--first` при ручном запуске с «Первой публикацией»), артефакт `dist-release`, сводка и отчёт.
- **«Публикация»** — окружение GitHub `npm` (публиковать из него можно только из `main`), право только `id-token: write`, без checkout и `pnpm install`.
  - npm не ниже 11.5.1; `NODE_AUTH_TOKEN` — только если есть временный секрет `NPM_TOKEN`.
  - Каждое поле плана сверяется с образцом; SHA-512 архива и имя с версией внутри — с планом.
  - Перед каждым пакетом — реестр ещё раз:
    - версия уже вышла этим же архивом (SHA-512) — пропуск, поэтому повторный запуск безопасен;
    - вышла другим архивом — стоп: зависящие от неё пакеты собраны из другого кода;
    - номер снят — стоп;
    - под `next` не та версия, от которой считал план, — «план устарел»;
    - новый пакет без токена — ошибка с подсказкой.
  - `npm publish ./dist-release/{архив}.tgz --tag next --access public --provenance --ignore-scripts`. Путь — с `./`: без него npm принимает путь к архиву за репозиторий GitHub (проверено 29 октября 2026). npm публикует архив как есть: SHA-512 в пробной публикации совпал с планом.
  - Порядок — ядро, тег, React; на первом сбое — стоп.
- **«Проверка»** — `pnpm release verify` (ждёт 15 минут после публикации, 2 — после сбоя), затем `pnpm starters html --check --npm --browser=chrome`: строка из README с хэшем, настоящий jsDelivr и живые хосты в браузере.
- «Живой» запуск — `main`, не PR и не «только показ». Проверки «main ушёл вперёд», как в «Публикации в npm», нет: запуск собирает свой коммит, а версию, которая уже вышла или не выше вышедшей, подготовка не пропустит.
- **Проверено ревью 29 октября 2026** (`/code-review` уровня high, до публикации): повторный `bump` без версии после выхода портил бы хэш README, «СТОП» на `main` не перезапускался бы, «Только показ» мог отменить ждущий выпуск, повтор публикации пропускал бы вышедшую версию, не сверив архив, — всё исправлено до 0.1.0.
- **Не переименовывайте `release.yml`, окружение `npm` и репозиторий:** к ним привязана доверенная публикация на npmjs.com.

## Первая публикация и доверенная публикация

У несуществующего пакета доверенную публикацию npm не включить (ADR-0026), а настройка, через которую ни разу не публиковали, через 48 часов истекает (GitHub, 2 октября 2026). Поэтому:

- 0.1.0 выходит ручным запуском с «Первой публикацией» и временным токеном — с provenance;
- сразу после неё токен отзывается, а у пакетов включается «Require two-factor authentication and disallow tokens» — с этой настройкой доверенная публикация работает (так у пакетов данных с 23 октября 2026);
- доверенная публикация включается прямо перед первым выпуском через неё, 0.1.1, и он сливается в течение 2 дней.

**Настройки — ставит владелец; дословно.** Окружение `npm` — то же, что у пакетов данных (ADR-0026).

Перед первой публикацией 0.1.0:

1. Временный токен: npmjs.com → аватар → Access Tokens → Generate New Token.
   - Expiration — самый короткий срок (не меньше суток).
   - Bypass two-factor authentication ✓.
   - Allowed IP Ranges — пусто: адреса машин GitHub меняются.
   - Packages and scopes — Permissions «Read and write (publish and stage)», Only select packages and scopes → `@iconavo-ui`.
   - Organizations — No access.

   Токен — сразу в секрет окружения, не в чат и не в файлы: GitHub → Settings → Environments → `npm` → Environment secrets → `NPM_TOKEN`. Пакеты данных токен не возьмут: у них токены запрещены, а npm сначала пробует доверенную публикацию.
2. Actions → «Выпуск пакетов» → Run workflow, ветка `main`, «Первая публикация» ✓. Дождаться зелёных «Подготовки», «Публикации» и «Проверки» — до 15 минут. Если «Публикация» упала посередине — секрет не удалять и повторить запуск не раньше чем через 5 минут: вышедшие пакеты он пропустит.
3. Когда «Проверка» зелёная у всех трёх: удалить секрет `NPM_TOKEN` и отозвать токен на той же странице npmjs.com.
4. У каждого пакета `@iconavo-ui/core`, `@iconavo-ui/icon`, `@iconavo-ui/react`: npmjs.com → пакет → Settings → Publishing access → «Require two-factor authentication and disallow tokens» → Update Package Settings.
5. Посмотреть страницу `@iconavo-ui/icon` на npmjs.com: 0.1.0, значок provenance, теги `latest` и `next`, README.

Перед выпуском 0.1.1 — первым через доверенную публикацию:

6. Когда PR выпуска зелёный, у каждого из трёх пакетов: npmjs.com → пакет → Settings → Trusted Publisher → GitHub Actions.
   - Organization or user — `iconavo`.
   - Repository — `iconavo`.
   - Workflow filename — `release.yml`.
   - Environment name — `npm`.
   - Allowed actions — ✓ npm publish; npm dist-tag не нужен. С 3 сентября 2026 у новой настройки по умолчанию отмечен только stage publish.
7. В течение 2 дней слить PR: CI опубликует сам, «Проверка» покажет «доверенная публикация». Не успели — удалить настройку и создать заново.

С января 2027 npm перестанет пускать токены с обходом двухфакторной защиты к прямой публикации (ADR-0026): новый пакет тогда выходит через `npm stage publish` — бэклог.

## Примеры после выпуска

- `pnpm release bump` ставит новую версию примерам React и Next.js и удаляет их lock-файлы с прошлой версией. Тест согласованности lock-файлов не требует, но если они есть — они совпадают с `package.json` и берут наши пакеты из реестра npm.
- После публикации — PR с lock-файлами (`pnpm starters --lock`) и `pnpm starters --check --npm`: примеры как у разработчика — `npm ci`, живые хосты, настоящий jsDelivr.
- Локальная проверка примеров (`pnpm starters --check`) подменяет jsDelivr сборкой ветки, поэтому в рабочей копии HTML-примера хэш — от этой сборки. Контрольный запуск подменяет скрипт файлом с лишней строкой: браузер обязан его не запустить, иначе проверка слепая.

Почему: три пакета, которые разработчик ставит вместе, выходят вместе и с одним журналом. Слияние PR — понятное владельцу «да» без доступа к npm, а подпись provenance, проверка архива и чистый проект после публикации доказывают, что в npm ровно то, что прошло проверки в `main`.
