# Фаза 1 подробно: данные и конвейер

За шесть недель вы вместе с Claude Code строите «фабрику»: она забирает наборы иконок у авторов, чистит, обогащает описаниями и сохраняет в вашем формате, готовыми к смысловому поиску. Вы отвечаете за решения и проверку результата, Claude Code — за код.

Технические решения фазы записаны в ADR-0012…0021, и промпты ниже на них опираются. Продуктовые решения ждут вашей отметки там же: Решения (ADR)

## Как работать с Claude Code

Ваша роль — продакт и контролёр качества: вы ставите задачу, принимаете план и проверяете результат глазами. Код пишет Claude Code, а задача не считается сделанной без доказательства. Этот цикл одинаков для фаз 1–3.

Цикл одной задачи:

1. Новая сессия на каждую задачу: `/clear`, чтобы старый разговор не мешал.
2. План: `/plan` и описание задачи. Claude изучает проект и предлагает план, ничего не меняя.
3. Вопросы к плану: просите объяснить непонятное простыми словами и правьте план, пока он вас не устроит.
4. Выполнение: одобрите план — Claude пишет код и запускает тесты.
5. Доказательство: просите результат в понятном виде — HTML-страницу с превью, отчёт, вывод проверки. Для готовых приложений есть навык `/verify`: Claude сам запускает проект и смотрит на результат.
6. Обзор: `/diff` показывает, что поменялось, а `/code-review` ищет ошибки в изменениях.
7. Фиксация: попросите коммит с понятным описанием. Одна проверенная задача — один коммит.

Правила, которые экономят недели:

- Одна задача за раз. Просьба «сделай весь конвейер» даёт код, который вы не сможете проверить.
- Не принимайте «готово» на слово. Спрашивайте: «Как мне убедиться, что это работает? Покажи».
- Если Claude ушёл не туда, нажмите Esc дважды или введите `/rewind` и откатите код и разговор к контрольной точке.
- В длинном разговоре `/context` покажет заполненность, а `/compact` сожмёт историю.
- Новые зависимости — только с вашего согласия и с объяснением, зачем они нужны.
- Токены и пароли никогда не вставляйте в чат и не храните в репозитории.

Лимиты подписки Max 5x показывает `/usage`. Дороже всего обходятся переделки, поэтому план в начале — главная экономия; при исчерпании лимита `/rate-limit-options` подскажет варианты. Если удобнее окно, а не терминал, `/desktop` переносит сессию в приложение Claude Code Desktop.

Справочник всех команд: [code.claude.com/docs/en/commands](https://code.claude.com/docs/en/commands).

## Словарь фазы

| Термин | Что это простыми словами |
| --- | --- |
| SVG | Векторная картинка, описанная текстом: фигуры, линии, цвета |
| viewBox | «Холст» иконки: координаты и размер области, где нарисованы фигуры |
| currentColor | Цвет «как у текста»: иконка перекрашивается вместе с текстом вокруг |
| Набор иконок | Коллекция одного автора в одном стиле, например Lucide |
| Схема данных | Договор о том, как устроен файл набора: какие поля есть и какого они типа |
| Валидатор | Программа, которая проверяет файл по схеме и называет ошибки |
| Реестр источников | Список наборов: откуда скачивать, какая лицензия, как обрабатывать |
| npm | Каталог JavaScript-пакетов; многие наборы иконок публикуются там |
| Коммит | Сохранённая версия кода в git с описанием изменений |
| Санитайзер | Фильтр, который удаляет из SVG всё опасное и лишнее |
| SVGO | Популярный оптимизатор, который уменьшает SVG без видимых изменений |
| Детерминированность | Одинаковый вход всегда даёт побайтно одинаковый результат |
| Хэш | Короткий отпечаток содержимого: изменился файл — изменился отпечаток |
| Рендер | Превращение SVG в картинку из пикселей, например PNG |
| CI | Автоматические задачи на серверах GitHub: при каждом изменении или по расписанию |
| Pull request (PR) | Предложение изменений, которое можно посмотреть и принять |
| ADR | Короткая запись архитектурного решения: что решили и почему |

## Подготовка

До первого шага нужны рабочее окружение, репозиторий и файл с правилами для Claude Code. Это примерно полдня, и большую часть сделает сам Claude.

- [ ] Аккаунт GitHub с двухфакторной аутентификацией.
- [ ] Git и Node.js в LTS-версии на компьютере — их проверка и установка станут первой просьбой к Claude Code.
- [ ] По желанию GitHub Desktop, чтобы видеть историю изменений без терминала.
- [ ] Папка проекта, в ней запущен Claude Code и выполнена команда `/init` — она создаст первый CLAUDE.md.
- [ ] Решения фазы 0 лежат в папке `docs/adr/`.
- [ ] Репозиторий на GitHub, ветка `main` защищена от прямых изменений — настройку попросите у Claude Code.

Первый промпт:

```
Я продуктовый дизайнер, не разработчик. Мы строим платформу иконок. Проверь, что у меня установлены Git, Node.js LTS и pnpm, и помоги поставить недостающее. Потом создай монорепозиторий на TypeScript с pnpm workspaces: packages/pipeline для конвейера, sources/ для реестра наборов, data/ для результатов, docs/adr/ для решений. Объясняй каждый шаг простыми словами.
```

Что дописать в CLAUDE.md после `/init`:

```markdown
# Iconavo — платформа иконок
Я продуктовый дизайнер, не разработчик. Объясняй простыми словами.

## Правила
- Если меняешь больше двух файлов — сначала план.
- После изменений запускай тесты и показывай результат.
- Всё, что нужно оценить глазами, показывай HTML-страницей.
- Новые зависимости — только после моего согласия.
- Никогда не коммить токены, пароли и файлы .env.
- Один шаг — один коммит с понятным описанием на русском.

## Решения
См. docs/adr/. Если решения нет — спроси, не придумывай.

## Команды
Допиши сам: как запускать конвейер, тесты и галерею.
```

## Шаги 1–3: схема, реестр, очистка

Первые три шага дают основу: формат файла, список источников и очистку SVG. Начинайте с Lucide — это самый простой из пяти наборов.

### Шаг 1. Схема данных и валидатор, ≈3 дня

Зачем: схема фиксирует, как устроен файл набора, чтобы все части проекта понимали его одинаково.

```
/plan Фаза 1, шаг 1. По решениям из docs/adr/ создай схему данных набора иконок: типы TypeScript и валидатор на zod. Отдельно — схема метаданных (теги, категории, лицензия), она не попадает в рантайм. Имена: только a-z, 0-9 и дефис. Добавь два примера: правильный файл и сломанный с тремя разными ошибками. Напиши тесты и одну команду для проверки любого файла.
```

Как проверить:

- На правильном примере команда проверки не находит ошибок.
- На сломанном — три понятные ошибки с указанием поля.
- Попросите: «Покажи пример файла и объясни каждое поле». Поле, которое вы не понимаете, стоит переименовать или убрать.

Готово, когда тесты проходят и вы можете своими словами объяснить формат.

### Шаг 2. Реестр источников и загрузчики, ≈3 дня

Зачем: каждый набор описан одним конфигом, и конвейер сам скачивает нужную версию. Ваша часть — найти для каждого набора репозиторий, npm-пакет и файл лицензии.

```
/plan Фаза 1, шаг 2. Сделай реестр источников в sources/: один конфиг на набор (id, тип источника npm или git, пакет или репозиторий, путь к SVG, правило имён, монохромный или цветной, лицензия). Напиши загрузчик: скачивает нужную версию, запоминает версию или коммит и не качает повторно без изменений. Начни с Lucide. Покажи отчёт: что скачано, сколько файлов, какая версия.
```

Как проверить:

- Первый запуск скачивает набор и показывает версию и число файлов.
- Повторный запуск сообщает, что изменений нет, и ничего не качает.
- Число файлов примерно совпадает с числом иконок на сайте набора.

Готово, когда все пять наборов скачиваются одной командой.

### Шаг 3. Очистка SVG, ≈3 дня

Зачем: тела иконок будут вставляться в страницы чужих сайтов, поэтому в них не должно остаться ничего исполняемого и лишнего.

```
/plan Фаза 1, шаг 3. Сделай санитайзер SVG по белому списку элементов и атрибутов. Удалять: script, foreignObject, image, обработчики on*, внешние ссылки (оставлять только #id), метаданные редакторов, комментарии. style и классы из <style> переводить в атрибуты. XML-парсер — с отключёнными DTD и сущностями. Собери 15 «вредных» тестовых SVG и тесты на них. Выведи отчёт: что и сколько удалено в каждом наборе.
```

Как проверить:

- Все «вредные» примеры очищены, тесты проходят.
- В отчёте нет иконок, у которых удалено почти всё, — это признак слишком строгого фильтра.
- Попросите показать три иконки до и после очистки на одной странице.

Готово, когда отчёт понятен и ни одна иконка Lucide визуально не сломалась.

## Шаги 4–6: нормализация, оптимизация, контроль

Эти шаги превращают очищенные SVG в единообразные иконки и дают вам главный инструмент контроля — галерею.

### Шаг 4. Нормализация, ≈4 дня

Зачем: иконки разных авторов приводятся к одному виду, чтобы перекрашиваться, масштабироваться и не конфликтовать на странице.

```
/plan Фаза 1, шаг 4. Нормализуй иконки: гарантируй viewBox, сними width и height с корня, перенеси атрибуты корня (fill, stroke, stroke-width и другие) во внешний <g>. Монохромные цвета замени на currentColor, fill="none" не трогай, фигурам без fill задай цвет явно. ID масок и градиентов префиксуй именем набора и иконки. Сделай HTML-галерею: каждая иконка оригиналом и результатом, на светлом и тёмном фоне, в красном цвете, в размерах 16, 24 и 48 px.
```

Что смотреть в галерее:

- Результат совпадает с оригиналом по форме.
- В красном цвете перекрашена вся монохромная иконка, а не её часть.
- Линейные иконки (Lucide, Tabler) не превратились в залитые силуэты.
- На тёмном фоне иконки видны: цвет берётся от текста.
- Fluent Emoji сохранили свои цвета.

Готово, когда вы пролистали галерею всех пяти наборов и не нашли расхождений.

### Шаг 5. Оптимизация и детерминированный вывод, ≈2 дня

Зачем: файлы становятся меньше, а повторная сборка даёт тот же результат — иначе каждое обновление будет казаться изменением.

```
/plan Фаза 1, шаг 5. Подключи SVGO с явным конфигом: viewBox не удалять, точность чисел подобрать под сетку набора, анимации не трогать. Сделай вывод детерминированным: порядок атрибутов, формат чисел, порядок иконок. Добавь тест: две сборки подряд дают побайтно одинаковые файлы. Покажи отчёт: размер до и после по каждому набору.
```

Как проверить:

- Отчёт показывает, насколько уменьшились файлы.
- Тест на повторную сборку проходит.
- В галерее формы не изменились после оптимизации.

Готово, когда повторная сборка не даёт ни одного изменения.

### Шаг 6. Контроль качества, ≈4 дня

Зачем: тысячи иконок глазами не проверить, поэтому машина находит подозрительные, а вы смотрите только их.

```
/plan Фаза 1, шаг 6. Сделай автоматический контроль: рендер каждой иконки в PNG через resvg, поиск пустых (нет закрашенных пикселей) и обрезанных (фигуры выходят за viewBox), попиксельное сравнение с прошлой версией через pixelmatch. Итог — HTML-отчёт: подозрительные иконки с картинками и причиной, изменившиеся — с наложением «было/стало». Сборка падает, если есть пустые иконки.
```

Как проверить:

- Попросите Claude специально сломать одну иконку — отчёт её находит.
- Пустых иконок ноль, а каждая обрезанная разобрана: ошибка или так задумано автором.

Готово, когда отчёт открывается одной командой и вы понимаете каждую строку.

## Шаги 7–9: метаданные, журнал, автообновление

Последние шаги делают конвейер самостоятельным: он знает авторов и лицензии, ведёт журнал и обновляется без вас.

### Шаг 7. Метаданные и лицензии, ≈2 дня

Зачем: теги нужны поиску на сайте, а лицензии — юридической чистоте каждого пакета.

```
/plan Фаза 1, шаг 7. Для каждого набора импортируй теги и категории из метаданных источника, если они есть (у Lucide, например, рядом с SVG лежат JSON-файлы). Где их нет — теги из частей имени. Сохраняй SPDX-идентификатор лицензии, полный текст LICENSE, файл NOTICE (если есть), ссылку на источник и коммит. Покажи таблицу: набор, лицензия, число иконок с тегами.
```

Как проверить:

- У каждого набора есть лицензия и её текст.
- Откройте 10 случайных иконок: теги похожи на правду.

Готово, когда таблица заполнена для всех пяти наборов.

### Шаг 8. Хэши, журнал изменений, переименования, ≈2 дня

Зачем: пользователи должны видеть, что изменилось, а старые имена иконок — продолжать работать.

```
/plan Фаза 1, шаг 8. Считай хэш содержимого каждой иконки. При каждой сборке формируй журнал по набору: добавлены, удалены, изменены. Удалённые иконки не удаляй, а помечай deprecated. Если тело новой иконки совпадает с удалённой — предлагай алиас. Журнал — в markdown, понятный человеку.
```

Как проверить: попросите Claude смоделировать обновление — удалить одну иконку и переименовать другую. В журнале должны быть видны удаление и предложенный алиас.

Готово, когда журнал читается без пояснений.

### Шаг 9. Автообновление в CI, ≈2 дня

Зачем: авторы обновляют наборы, и конвейер должен забирать изменения сам, а вы — только одобрять.

```
/plan Фаза 1, шаг 9. Настрой GitHub Actions: раз в сутки по расписанию запускать конвейер для всех наборов. Если есть изменения — открыть pull request с журналом изменений и ссылкой на отчёт контроля качества. Если найдены пустые иконки — помечать PR как проблемный. Объясни, где смотреть результаты запусков.
```

Как проверить: запустите задачу вручную на вкладке Actions в GitHub — должен прийти PR с журналом, который можно прочитать и принять. Команда `/install-github-app` подключит Claude к репозиторию, и он сможет разбирать такие PR вместе с вами.

Готово, когда вы приняли первый автоматический PR.

## Шаги 10–12: обогащение, эмбеддинги, прототип поиска

Эти шаги превращают конвейер в основу смыслового поиска — главной фичи проекта. Решения записаны в ADR-0009 и ADR-0010 на вкладке «Решения (ADR)».

### Шаг 10. Обогащение ИИ, ≈3 дня

Зачем: у многих наборов мало тегов, и почти все они на английском. Модель смотрит на иконку и пишет описание и синонимы на русском и английском.

```
/plan Фаза 1, шаг 10. Добавь в конвейер обогащение: для каждой иконки отрендерь PNG и отправь модели, которая понимает изображения, вместе с именем и тегами. Модель возвращает JSON: описание в одно предложение и 5–10 синонимов на русском и английском. Кэшируй результат по хэшу иконки, отправляй задачи пакетно, ключ API бери из переменных окружения. Начни с 50 иконок Lucide и покажи HTML-страницу: иконка, описание, синонимы, стоимость прогона.
```

Как проверить:

- Пролистайте страницу с 50 иконками: описания и синонимы соответствуют картинке.
- Повторный запуск не отправляет модели те же иконки заново.
- По стоимости прогона посчитайте бюджет на весь каталог.

Готово, когда ошибочных описаний на выборке почти нет, а стоимость всего каталога посчитана.

### Шаг 11. Эмбеддинги, ≈2 дня

Зачем: векторы позволяют находить иконку по смыслу, даже если в запросе нет ни одного слова из её имени.

```
/plan Фаза 1, шаг 11. Для каждой иконки собери текст из имени, тегов, описания и синонимов и посчитай эмбеддинг. Подключи 2–3 многоязычные модели эмбеддингов из короткого списка и сохрани векторы отдельно для каждой. Кэшируй по хэшу текста. Объясни простыми словами, чем модели отличаются по цене и скорости.
```

Как проверить: попросите показать пять иконок, ближайших по смыслу к запросу «корзина» и к запросу «trash». Списки должны почти совпасть.

Готово, когда векторы посчитаны для всех пяти наборов во всех моделях из списка.

### Шаг 12. Прототип поиска и первый замер, ≈3 дня

Зачем: поиск — главная фича, и его качество нужно увидеть как можно раньше, ещё до сайта.

```
/plan Фаза 1, шаг 12. Сделай прототип гибридного поиска: текстовая часть по именам, тегам и синонимам плюс векторная по эмбеддингам, результаты сливаются, точное совпадение имени наверху. Добавь страницу поиска для ручной проверки и скрипт замера: по эталону из docs/eval/ считать долю запросов с нужной иконкой в первой пятёрке, отдельно для русского и английского и для каждой модели.
```

Как проверить:

- Попробуйте на странице поиска 20 своих запросов на русском и смотрите первую пятёрку.
- Отчёт замера показывает цифры по каждой модели; лучшую зафиксируйте в ADR-0010.

Готово, когда есть первый замер, выбранная модель и цель качества к запуску.

## Проверка готовности фазы

Фаза закрыта, когда все пункты ниже — «да». Проверяйте сами, а не по отчёту Claude.

- [ ] Пять наборов скачиваются и собираются одной командой.
- [ ] Повторная сборка без изменений в источниках даёт ноль изменений.
- [ ] Отчёт контроля качества: ноль пустых иконок, обрезанные разобраны.
- [ ] Галерея пролистана целиком, расхождений с оригиналами нет.
- [ ] У каждого набора есть лицензия, её текст, источник и коммит.
- [ ] Журнал изменений формируется и читается без пояснений.
- [ ] Автоматический PR из CI пришёл и принят.
- [ ] CLAUDE.md описывает все команды конвейера.
- [ ] Описания и синонимы проверены на выборке, стоимость обогащения всего каталога посчитана.
- [ ] Прототип поиска дал первый замер по эталону, модель эмбеддингов выбрана.

## Если что-то пошло не так

| Симптом | Вероятная причина | Что сказать Claude Code |
| --- | --- | --- |
| Линейные иконки стали чёрными силуэтами | Атрибуты корня потерялись при снятии `<svg>` | «Проверь, что fill="none" и stroke с корня перенесены во внешний `<g>`» |
| Часть иконки не перекрашивается | В иконке остался жёсткий цвет | «Найди в монохромных наборах цвета, кроме currentColor, и покажи список» |
| Иконки обрезаны или сдвинуты | Неверный viewBox или трансформация на корне | «Сравни viewBox до и после для этих иконок и объясни разницу» |
| Формы искажены после оптимизации | Слишком грубое округление чисел | «Увеличь точность чисел для этого набора и сравни в галерее» |
| Каждая сборка показывает изменения | Вывод не детерминирован | «Найди, что меняется между двумя сборками подряд» |
| Загрузчик падает после обновления набора | Автор поменял структуру папок | «Покажи, что изменилось в источнике, и предложи правку конфига» |
| Claude наломал лишнего | Слишком большая задача или неясный промпт | `/rewind`, затем `/clear` и задача поменьше |
| Ответы стали путаными | Переполнен контекст | `/context`, затем `/compact` или новая сессия |
